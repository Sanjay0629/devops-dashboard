## 0. What M4.2 is, and what it is not

**Is** (IMPLEMENTATION_PLAN): the state machine with guarded transitions and illegal-transition errors; `deadline_at`; the timeout reaper; the one-in-flight partial unique index in use; idempotency; the `operations` Celery queue; worker-side re-authorisation and target re-validation; endpoints 17.1 – 17.3; the frontend confirmation dialog, progress polling and result display.
**Acceptance (PRD §4.6):** a user without permission cannot start / stop / restart; an *approved* restart creates an operation record (see D2 for what "approved" can mean before M4.5); the UI shows the execution result **and the verified service state**; failed operations preserve redacted diagnostics; duplicate requests do not execute twice.
**Is not:** a real provider (AWS M4.3, Azure M4.4), the approval workflow and the `approvals` table (M4.5), endpoints 22.1 – 22.4 (D1), the history and audit APIs (M4.6), a retry trigger (D11).
**The sentence to hold on to afterwards:** M4.2 builds the machine and proves it against a test fake. In the shipped application **no operation can be created yet**, because the adapter registry ships empty and the demonstration adapter refuses every write (D10). That is the honest state (CLAUDE.md §7), not a gap to paper over.

## 1. Findings that shaped the decisions

1. **IMPLEMENTATION_PLAN lists 22.1 – 22.4 under M4.2, and M4.5 lists the same approval endpoints.** The `approvals` table does not exist (`approvals/models.py`: "arrives in M4.5"), and 22.1 – 22.4 read it. M4.2 cannot build them. (D1)
2. **There is no approval workflow, yet the request path must "evaluate the approval policy".** A request that needs approval has nowhere to go. Creating `AWAITING_APPROVAL` rows that nobody can decide would hold the target's single in-flight slot and leave stale production intent. (D2)
3. **`VERIFYING` (AD-09) is not storable.** `DATABASE.md` §6 and API_CONTRACTS §9 give `execution_status` exactly the PRD's nine values. (D3)
4. **The state diagram has no exit for a row that is never claimed.** A `PENDING` row whose queue message is lost holds the one-in-flight slot forever. (D3, D4)
5. **Two documents disagree about a worker crash.** IMPLEMENTATION_PLAN says the reaper times the row out "and does **not** re-invoke"; TESTING §7 also says "worker restart mid-poll resumes from the persisted handle". Resuming needs a real provider to resume against. (D4)
6. **The two idempotency orders differ.** `SECURITY.md` §16 puts the replay check *after* the rate limit and the one-in-flight guard; `ARCHITECTURE.md` §3.2 puts it first. Taken literally, §16 makes a replay of a still-running operation fail with `409 operation_in_progress` instead of returning the original. (D8)
7. **The worker needs the requester's grants and only an async resolver exists** (`authz.service.resolve_grants` takes `AsyncSession`; workers are synchronous). Writing a second copy of the permission rules is the thing to avoid. (D6)
8. **`service_action_policies.max_concurrent_operations` cannot be honoured above 1:** the partial unique index in the contract is per `(server, service)`. SECURITY §13 says one in flight, so the column is effectively fixed at 1. (D8)
9. **The contract lets `status` and `logs_tail` into `operations.action_type` but §17.1 accepts only `start | stop | restart`.** Status is §16.4 and logs are §16.7 already. (D1)
10. **`parent_operation_id` has no trigger.** §17.1's body is closed (`action`, `reason`) and there is no retry endpoint. (D11)
11. **`services/router.py` §16.6 says "the in-flight-operation guard arrives with `operations`"** — a deregister during an operation is M4.2's to refuse. (D8)
12. **`PRD §4.6` acceptance "an approved restart creates an operation record"** is satisfied for targets with no approval requirement; for gated targets it completes in M4.5. Stated in D2 so it is not read as met earlier than it is.

## 2. Decisions (closed, recommended option taken)

### D1 — `OPEN-67` Scope: 17.1 – 17.3 only; 22.x moves to M4.5
M4.2 builds §17.1, §17.2, §17.3. **22.1 – 22.4 move to M4.5**, where the `approvals` table, the self-approval rule and the approver queue are. IMPLEMENTATION_PLAN's M4.2 task line is amended. §17.1 accepts `start | stop | restart` only; `status` and `logs_tail` stay in the table's CHECK (the contract's enum) but are `422` at §17.1, because §16.4 and §16.7 already serve them and a "status operation" would be a state-changing record of a read. *Rejected:* building a stub 22.x now (mock data, CLAUDE.md §7).

### D2 — `OPEN-68` Approval before M4.5: evaluate, and fail closed
A pure evaluator `approval_required(policy, approval_policy, environment, action)` is built and used on both sides. It returns *required* when **any** of: the service's action policy links an approval policy whose `applies_to = SERVICE_OPERATION` and whose `environment` is the operation's environment or `*`; the action is `stop` and the environment is `production` (SECURITY §16: "`stop` on a production service … defaults to requiring approval", independent of any row); the linked policy row is missing or unreadable (fail closed).
- **At request time:** *required* ⇒ **`503 not_configured`, reason `approval_workflow_unavailable`, no row created, audited `SERVICE_OPERATION_DENIED`.** `AWAITING_APPROVAL`, `APPROVED` and `REJECTED` exist in the table, the CHECK and the machine, but **no M4.2 code path enters them**.
- **In the worker:** a claimed row for which the evaluator says *required* and whose `approval_status` is not `APPROVED` is refused (`APPROVAL_REQUIRED`) with zero provider calls. This is mandatory rule 3's "re-checked by the worker", and it is testable now by inserting such a row directly.
- **Reason text:** required when the environment is `production` or approval is required; 1 – 500 characters.
*Rejected:* creating `AWAITING_APPROVAL` rows that only the requester can cancel (wedges the target through the one-in-flight index; the expiry sweep is M4.5). *Consequence:* until M4.5, a production restart under the seeded `production-service-operations` policy cannot be requested at all. That is fail-closed, and it is stated in the UI.

### D3 — `OPEN-69` The state machine: a table, `VERIFYING` never stored, two edges added
`app/operations/states.py`: the transition table as data, `legal(from, to)`, and `public_status(state)`. Every status change goes through one persistence function — a guarded `UPDATE … WHERE id = :id AND execution_status = :from … RETURNING` — and a zero-row result raises `InvalidTransition` (API: `409 invalid_state_transition`; worker: exit without side effects). Illegal means "not in the table"; there is no per-call special casing.
- **`VERIFYING`** is in the table and in `public_status` (it maps to `RUNNING`, TESTING §7), but **is never written**: the column's CHECK is the PRD's nine values. A `RUNNING` row is `RUNNING` in the database whether the worker is submitting, polling or verifying. AD-09's text is amended to say so.
- **Two edges are added to ARCHITECTURE §6.2:** `PENDING → TIMED_OUT` and `APPROVED → TIMED_OUT`, written **only by the reaper**, with `failure_reason = EXPIRED_BEFORE_START`, never calling a provider. Without them an unclaimed row past its deadline has no legal exit. *Rejected:* the reaper claiming the row and timing it out from `RUNNING` (the audit trail would say the operation started when it did not).
- Terminal states (`SUCCEEDED | FAILED | TIMED_OUT | CANCELLED | REJECTED`) have no outgoing edges.

### D4 — `OPEN-70` Execution shape: one task, no resume, a reaper and a healer
`workers/tasks/operations.py::execute_operation(operation_id)` on the `operations` queue (id only; JSON; `acks_late` and the 4 h visibility timeout already configured). One task does: re-authorise and re-validate (D6) → claim → pre-flight read → `execute_operation` → **persist `external_execution_id` in its own committed transaction before any poll** → poll → verify (D7) → finalise, with outcomes as in D5. Hard/soft Celery time limits above the largest policy deadline (3 600 s), so a stuck task is terminal.
- **No resume.** A worker killed mid-operation leaves a `RUNNING` row; a second delivery loses the claim and exits. The reaper moves it to `TIMED_OUT` at `deadline_at` with `sanitized_result.reconciliation_required = true` (set whether or not a handle was recorded; the handle is kept so an operator can look the execution up) and **never re-invokes the provider**. "Resumes from the persisted handle" (TESTING §7) moves to M4.3 — it needs a provider with something to resume — and TESTING is amended.
- **Reaper and healer** are one beat task on the **`maintenance`** queue (so a saturated `operations` queue cannot stop them): every 30 s, `RUNNING` past `deadline_at` → `TIMED_OUT` `DEADLINE_EXCEEDED`; `PENDING` / `APPROVED` past `deadline_at` → `TIMED_OUT` `EXPIRED_BEFORE_START`; `PENDING` / `APPROVED` unclaimed for over 30 s and not past deadline → re-enqueue (idempotent: the claim is guarded). The enqueue in the request is after the commit and best-effort; the healer is what makes "DB first" (ARCHITECTURE §14.1) recoverable.
- **Deadline:** `deadline_at = created_at + service_action_policies.operation_timeout_seconds` (10 – 3 600 s, default 300). The clock starts at the request and includes queue wait.
- Poll interval 1, 2, 4, then 5 s; healer age 30 s; reaper period 30 s — module constants named as working defaults, not measurements.

### D5 — `OPEN-71` Provider outcomes: what each means for the row
| Provider event | Row ends | `failure_reason` | `reconciliation_required` |
|---|---|---|---|
| Re-check refuses (D6) | `FAILED` | `PERMISSION_REVOKED`, `APPROVAL_REQUIRED`, `ACCOUNT_DISABLED`, `ACTION_NOT_ALLOWED`, `TARGET_VALIDATION_FAILED` | no (nothing was sent) |
| `NotConfigured` / `UnsupportedOperation` / `AuthenticationError` / `AuthorizationError` / `NotFound` / `Throttled` on submit | `FAILED` | `NOT_CONFIGURED`, `UNSUPPORTED_OPERATION`, `PROVIDER_AUTHENTICATION`, `PROVIDER_AUTHORIZATION`, `PROVIDER_NOT_FOUND`, `PROVIDER_THROTTLED` | no (refused before acting) |
| `Timeout` after submit began | `TIMED_OUT` | `PROVIDER_TIMEOUT` | **yes** |
| `ProviderUnavailable` after submit began | `FAILED` | `PROVIDER_UNAVAILABLE` | **yes** |
| `PartialFailure` | `FAILED` | `PROVIDER_PARTIAL_FAILURE` | **yes** |
| Provider reports `FAILED` / `CANCELLED` | `FAILED` | `PROVIDER_REPORTED_FAILURE` | no |
| Provider reports `COMPLETED`, verification mismatches | `FAILED` | `VERIFICATION_MISMATCH` | no |
| Verification read not `ok` | `FAILED` | `VERIFICATION_UNAVAILABLE` | yes |
| Deadline passes while polling | `TIMED_OUT` | `DEADLINE_EXCEEDED` | **yes** |

**No state-changing call is ever retried by the worker** (CLAUDE.md §5; ARCHITECTURE §10.2's write column). `Throttled` is retryable in the table, but there is no real provider to throttle and a retry executor would be unexercised code; it is a terminal `FAILED` here and M4.3 decides whether to retry inside the invoke. The codes are a closed set in code; the column stays extensible for clients.

### D6 — `OPEN-71` (cont.) Worker re-authorisation and target re-validation
A synchronous grants resolver is needed. `resolve_grants`'s query and row-to-`Grant` conversion are **extracted to one shared function** and called by both the async and the new sync path; the permission rules are not copied. The worker's order, after the claim (so the denial is recorded against a row that really started, and `RUNNING → FAILED` is a legal edge): the requester still exists and is enabled → still holds `service:{action}` over the row's stored `environment` → approval evaluator (D2) → registry resolves an adapter and `ensure_supported` → server exists, not deleted, `MANAGED`, **its current environment equals the row's snapshot** (a re-labelled server is `TARGET_VALIDATION_FAILED`, in either direction) → cloud account `ACTIVE` (the `DISABLED` gate, SECURITY §14.3, deferred from M4.1) → the service row still belongs to that server, is not deleted, and its policy still allows the action → provider-side identity `get_server_info`. Any failure is a terminal `FAILED` (D5) with an audit row and **zero `_submit` calls**.

### D7 — `OPEN-72` Verification is a provider read, and `SUCCEEDED` needs it twice over
- **Before:** the pre-flight `list_managed_services(ref)` supplies `observed_state_before`; the unit being absent from the answer is `TARGET_VALIDATION_FAILED`.
- **After:** on `COMPLETED`, `list_managed_services(ref)` is read up to 3 times, 2 s apart, to let `ACTIVATING` / `DEACTIVATING` settle, bounded by the deadline. Expected state: `start` and `restart` → `ACTIVE`; `stop` → `INACTIVE`. `ACTIVE`/`INACTIVE` as expected ⇒ `SUCCEEDED` with `observed_state_after`, written in the same `UPDATE` as the status and `completed_at`. A read whose `data_state` is anything but `ok` — including `stale` — cannot prove an end state and is `VERIFICATION_UNAVAILABLE`.
- **`verified_at`** in §17.2 is derived from `completed_at` (written in the same statement); no column is added.
- **Two independent guards** (the milestone's stated worst failure mode): the machine refuses `→ SUCCEEDED` without a verification result, **and** `ck_operations_verified_success` refuses it in storage. Mutation checks prove each alone fails a test.
- *Prometheus is not the verifier.* Its 15 s scrape and lookback make "succeeded" depend on scrape timing, and `UNKNOWN` for a host that has just restarted is normal. It remains the platform's live display (the service page already shows it), shown beside the verified state, not feeding it. *Cost accepted:* verification reads from the same provider that acted. M4.3 may add an independent read; the column semantics do not change.

### D8 — `OPEN-73` The request path, idempotency, rate limit
Order for §17.1 (SECURITY §16 with one deliberate change): session → `Idempotency-Key` present (`422`) → body validated (`extra="forbid"`, `action` ∈ the three) → server exists, `MANAGED`, scope-visible (`404`) → service registered to *this* server (`404`) → account `ACTIVE` → action in the service policy's `allowed_actions` (`403`, audited) → caller holds `service:{action}` on the server's **stored** environment (`403`, `AUTHZ_DENIED`) → **idempotency lookup (replay)** → adapter resolves and the action is supported (D10) → approval evaluator (D2) → rate limit (5 / min / identity, privileged class: **fails closed** when Redis is unavailable, audited, `Retry-After`) → one-in-flight → insert row + audit in one transaction → commit → enqueue.
- **The replay lookup moves ahead of the rate limit and the one-in-flight guard** (finding 6), as ARCHITECTURE §3.2 already draws it. A replay returns `200` with the original resource and `idempotent_replay: true`, spends no rate-limit budget and executes nothing. SECURITY §16's diagram is amended to match.
- Key scope is the table's `UNIQUE (requested_by, idempotency_key)`. Body comparison: `(server_id, service_name, action, reason)`. A different body under the same key is `409 conflict` (`idempotency_key_reused_with_different_payload`).
- **The database is the guard, not the pre-checks.** Two concurrent submissions with one key → one wins, the loser's `IntegrityError` on `uq_operations_idempotency` is turned into a replay. A different key against a target with a live operation → `IntegrityError` on `uq_operations_single_inflight` → `409 operation_in_progress`. The courtesy pre-check exists only for a clean message.
- **Route permission:** the contract's permission is `service:{action}` and the action is in the body, so the route carries the explicit dependency `service:read` (the floor; read-only mode and `401` come with it) and the handler asks `authorized.permits("service", action, target)` and, on refusal, records `AUTHZ_DENIED` through `authz.service.record_denial` and returns `403`. The route-coverage meta-test sees an explicit permission dependency. Using the existing `_ACTION_PERMISSION` map, not a new one.
- **`max_concurrent_operations`** stays in the schema and is **not honoured above 1** (finding 8); recorded as a known issue, not silently ignored.
- **The in-flight guard for deregistration:** `DELETE …/services/{name}` (§16.6) and the server-retire path return `409 operation_in_progress` while an in-flight operation exists for the target.
- §17.3 cancel: legal only from `PENDING` / `AWAITING_APPROVAL` (the machine decides), by the requester or an `operation:approve` holder within scope; a `RUNNING` row is `409 invalid_state_transition`. A cancel that loses the race to a worker claim is that same `409`, never a false "cancelled".

### D9 — `OPEN-74` Results, visibility, and what is stored
`sanitized_result` is built from **closed fields only** in M4.2: `{adapter_id, steps[], observed_before, observed_after, reconciliation_required, reason_code}`. The adapter interface returns no free text (`ExecutionStatus.reason_code` is a closed code), so no provider words can reach the column; `redact()` is still applied to every string before persistence as defence in depth, and a canary test seeds a secret-shaped value into every path that writes it. Visibility for §17.2: `404` for an unknown operation or a server outside the caller's scope; the requester always; anyone else needs `operation:read` over the stored `environment`, else `403`. `sanitized_result` and `failure_reason` are returned on this detail endpoint only (the list is M4.6).

### D10 — `OPEN-75` Provider gating at the request: no row, an honest refusal
After the permission checks and before any row exists: `resolve_adapter(provider)` — demonstration mode ⇒ `503 not_configured` reason `demonstration_mode`; no adapter ⇒ `503 not_configured` reason `no_adapter_for_provider`; capability `unsupported` ⇒ `422 unsupported_operation` (PRD §4.11: never a generic failure); capability `not_configured` ⇒ `503 not_configured`. Every one is audited `SERVICE_OPERATION_DENIED` and creates no `operations` row. Ordering means a caller without permission learns nothing about how the portal is configured. **Consequence, stated plainly:** in the shipped application, with an empty factory map and a refusing demo adapter, §17.1 cannot create an operation. The full lifecycle runs only against `tests/providers/scripted.py` registered through the registry's test seam; no `app/` code simulates execution.

### D11 — `OPEN-76` Audit; `OPEN-77` frontend and what is deliberately not built
**Audit** (catalogue names already exist in API_CONTRACTS §28): `SERVICE_OPERATION_REQUESTED` (API, same transaction as the insert), `SERVICE_OPERATION_DENIED` (every refusal in D2 / D8 / D10 and every worker refusal), `SERVICE_OPERATION_CANCELLED`, `SERVICE_OPERATION_STARTED` (the claim), `SERVICE_OPERATION_COMPLETED` (any terminal state; the status and `failure_reason` in metadata). Each transition and its audit row commit **together** (ARCHITECTURE §14.7); if the audit write fails the transition does not happen (SECURITY §18). Worker rows carry `actor_id = requested_by`, `actor_label = "system:operations-worker"` and `on_behalf_of` in metadata (mandatory rule 7), all with the operation's `correlation_id`. The approval actions (`…_APPROVED`, `…_REJECTED`) are M4.5.
**Frontend** (OPEN-77): an *Actions* panel on the service detail page (buttons from the existing `allowed_actions` hint, which is a hint and never the control); a confirmation dialog restating **server, service, environment and action**, production visibly distinct, a required reason field for production, one `crypto.randomUUID()` Idempotency-Key per dialog open so a double click cannot duplicate; on `202` it navigates to a new `/operations/:id` page that polls §17.2 at `poll_after_seconds` until terminal and shows the status, `observed_state_before` / `observed_state_after`, the redacted failure diagnostics, and a cancel button while cancellable. It renders `503 not_configured` with the closed reason and `422 unsupported_operation` as "not supported by this provider", never as a generic error. `schema.ts` regenerated. No history list (M4.6).
**Deliberately not built:** 22.1 – 22.4 and the `approvals` table (M4.5); resume-from-handle (M4.3); a retry trigger — `parent_operation_id` is created and exposed as `null` but nothing sets it, because §17.1's body is closed and a `retry_of` field would be a contract change; the operation-failure **alert producer** (`operation_timed_out_or_failed` stays "not produced yet", per `OPEN-40`'s rule that a condition ships with the thing that can fail for real); `max_concurrent_operations` above 1; server-level operations (`target_service_id` NULL — the partial unique index treats NULLs as distinct, so it would not guard them); `status` / `logs_tail` through §17.1; a retry executor for provider calls; any real provider.

## 5. Security checklist

- No request field, task argument, adapter parameter or stored column accepts a command, script, argv, document name, URL or timeout override (a test walks the OpenAPI schema and the task signatures).
- Every route carries an explicit permission dependency; the per-action, per-environment check is also made in the handler and again in the worker.
- Mandatory rule 3: approval is evaluated at request time and re-checked by the worker; before M4.5 *required* means *refused*.
- Mandatory rule 6: an unreadable policy, grant, account, adapter or rate-limit backend is a denial.
- Mandatory rule 8: `SUCCEEDED` needs a verification read in code **and** in the schema.
- No state-changing provider call is retried; an ambiguous outcome is `reconciliation_required`, never a re-invoke.
- No provider text in any stored result or error; a canary sweep covers `sanitized_result`, audit metadata, logs and API responses.
- Every transition is audited with the same correlation id, in the same transaction.

## 6. Risks

- **A vacuous lifecycle test.** It runs against a fake that cannot fail unless told to. Mitigation: the fake is scripted to fail in each way D5 lists, and each failure is asserted to produce its row.
- **Over-claiming.** After M4.2 no real operation can run. The only honest summary is "the state machine exists and is proven against a test fake".
- **A silent diagram change.** D3 edits §6.2. That is why this plan asks for your reading before commit 1 writes it.
- **Touching M1.4 code.** Extracting the grants query is the only change to existing authorisation code; its existing tests must pass unchanged, and they are the proof the rules did not move.
- **The Celery singleton.** A test that imports the task module before the broker setting is applied makes every later registration retry its enqueue (PROGRESS M3.3). The task tests set the broker first.
- **Contract drift.** Seven documents change in commit 1; `check_doc_links.py` and a read of each diff against its neighbours is the control.

## 7. What would change this plan

If you want production operations requestable before M4.5 (D2), the alternative is creating `AWAITING_APPROVAL` rows with a requester-only cancel; it needs an expiry sweep, which is M4.5's, so it grows this milestone by a sweep and a partial `approvals` table. If you want the retry link (D11), it needs a contract decision on §17.1's body first.
