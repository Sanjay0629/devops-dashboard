## 0. What M5.2 is, and what it is not

**Is** (IMPLEMENTATION_PLAN, with one amendment, D1): the `deployments` table; endpoints 21.1, 21.2, 21.3, 21.6; the state machine; `external_execution_id` and the Jenkins queue id persisted **before** polling; a polling task with backoff and a deadline; `last_poll_error` surfaced; idempotency; one active deployment per application and environment; §21.12's in-flight guard; the deployment pages (list, request dialog, detail). **Acceptance (PRD §4.10):** an authorised user triggers a registered **non-production** pipeline; progress and result are visible; every deployment has a complete audit record; a failure shows useful diagnostics.

**Is not:** approve / reject (21.4, 21.5) and everything that needs an approver (M5.4); the console endpoint 19.3 and the log panel (M5.3); health-check execution, `HEALTH_CHECKS_FAILED` and rollback 21.7 (M5.5); aborting a running Jenkins build; more than one Jenkins; a deployment-failure alert producer; per-target deadlines.

**The sentence to hold on to afterwards.** After M5.1 DCP knew which pipelines it may run. After M5.2 it can *run* one and tell the truth about it — a non-production deployment is requested, triggered once, followed to a result and audited — while **a production deployment cannot be requested at all** (it needs M5.4's approvals, and fails closed until then). Like Phase 4 and M5.1 it is proven against a mock Jenkins only; no real Jenkins has been called.

## 1. Findings that shaped the decisions

1. **The contract lists approve and reject inside "21.1 – 21.6", and no one can decide a request yet.** Building them would mean a stub approver (mock behaviour, CLAUDE.md §7) or `AWAITING_APPROVAL` rows nothing can leave. M4.2 met the same problem and moved 22.x to M4.5. (D1, D2)
2. **Every production target must have an approval policy** (`OPEN-123`), so before M5.4 every production request needs an approval that cannot exist. The honest result is a refusal, not a queue. (D2)
3. **The state machine has no state between "decided to trigger" and "Jenkins has it".** `REQUESTED → QUEUED` is *"worker triggered the pipeline"*, but two workers must not both trigger, and the claim has to be visible **before** the call that cannot be retried. So the claim *is* the move to `QUEUED`, committed first; a `QUEUED` row with no queue id is then exactly "the trigger may have been sent". (D3, D6)
4. **Nowhere to put the queue id.** `external_execution_id` is the build; between the trigger and the build number there is a queue item. IMPLEMENTATION_PLAN's risk note says to persist it. (D4)
5. **A single long-sleeping Celery task per deployment** (the M4.2 shape) would hold a worker slot for up to an hour per deployment, and a killed worker would leave the row to the reaper. A due-row poller resumes by construction. (D5)
6. **The schema refuses `SUCCEEDED` with `health_check_result = '{}'`, and no target can register a health check until M5.5.** M5.1 handed this over (issue 197a). (D7)
7. **A trigger that times out may have queued a build** (`JenkinsError.may_have_acted`). Reconciling needs a read M5.1 did not write: find a build or queue item by the `deployment_id` parameter. A target registered without a `deployment_id` slot cannot be reconciled at all (issue 197e). (D6)
8. **The documents say the deadline is "target policy, default 3 600 s", and no target column holds one.** (D5)
9. **Editing a target between the request and the trigger would run something the requester never saw.** The deployment snapshots the pipeline reference (DATABASE §5.2) but not the template; a digest closes it. (D4, D6)
10. **`recent_deployments` on the dashboard is `not_configured` with `items: null`** and will become false the moment a deployment exists — the M4.6 / `OPEN-116` situation again. (D9)

## 2. Decisions (all closed at the recommended option)

### D1 — `OPEN-132` Scope; approve and reject move to M5.4
Built: migration `0015` (`deployments` only); endpoints **21.1, 21.2, 21.3, 21.6** and the 21.12 in-flight guard; the state-machine table; the success policy; the execute task, the poller, the reaper and healer; one Jenkins read (`find_by_parameter`, D6); `DCP_DEPLOYMENT_DEADLINE_SECONDS`; the dashboard's `recent_deployments`; the pages. **21.4 / 21.5 move to M5.4**, where the `approvals` rows and the decision rules for `applies_to = DEPLOYMENT` are used; IMPLEMENTATION_PLAN's M5.2 task line and API_CONTRACTS §21 are amended in commit 1. *Rejected:* a stub approver now.

### D2 — `OPEN-133` Approval before M5.4: evaluate, and fail closed
A pure `approval_required(target, environment)` is *required* when **any** of: the target's `approval_policy_id` is set; the environment is `production` (belt and braces — the API already demands a policy, a direct `UPDATE` would not); the linked policy row is missing or unreadable.
- **At request time:** *required* ⇒ `503 not_configured`, `details.reason = approval_workflow_unavailable`, **no row**, audited `DEPLOYMENT_DENIED`.
- **In the worker:** a claimed row whose target now requires approval and whose `approval_status` is not `APPROVED` is refused (`APPROVAL_REQUIRED`) with **zero Jenkins calls** (mandatory rule 3). Testable now by inserting such a row directly.
- `AWAITING_APPROVAL` and `APPROVED` exist in the table and the CHECK, **no M5.2 code path enters them**, and a test asserts that.
*Consequence, stated plainly:* until M5.4 no production deployment can be requested, and a non-production target with a policy cannot either. The UI says why.

### D3 — `OPEN-134` The state machine: a table, three added edges, the claim is `QUEUED`
`app/deployments/states.py`, as `app/operations/states.py` is: the legal `(from, to)` pairs as data, one guarded persistence function (`UPDATE … WHERE id = :id AND execution_status = :from … RETURNING`), a zero-row result is `409 invalid_state_transition` from the API and "exit without side effects" from a worker. Statuses are exactly PRD §4.10's nine.
Pairs: `AWAITING_APPROVAL → APPROVED | CANCELLED` (unused until M5.4); `REQUESTED → QUEUED` and `APPROVED → QUEUED` (**the worker's claim, committed before the trigger**); `REQUESTED → CANCELLED`; `QUEUED → RUNNING` (Jenkins assigned a build number); `QUEUED → CANCELLED` (**Jenkins reports the queue item cancelled** — DCP does not cancel it); `RUNNING → SUCCEEDED | FAILED`.
**Three edges are added to ARCHITECTURE §8.1:** `REQUESTED → FAILED` and `APPROVED → FAILED` (the reaper only: a row nobody claimed before its deadline, `EXPIRED_BEFORE_START`), and `QUEUED → FAILED` (a refusal by the worker's re-check, a trigger that was refused, a lost queue item, the deadline). There is **no `TIMED_OUT`**; a deadline is `FAILED` with `DEPLOYMENT_TIMED_OUT` (§21's own note). **No edge into `ROLLED_BACK`**: M5.5 adds it with the thing that uses it. A cancel is legal only from `REQUESTED` / `AWAITING_APPROVAL` (before any claim), by the machine; a `QUEUED` or `RUNNING` cancel is `409` — **aborting a Jenkins build is a state-changing provider call DCP does not make in M5.2**.

### D4 — `OPEN-135` Migration `0015` and the † columns
`deployments` exactly as DATABASE §5.2 (including its † columns, `UNIQUE (requested_by, idempotency_key)`, `CHECK (execution_status <> 'SUCCEEDED' OR health_check_result <> '{}')`, `CHECK ((kind = 'ROLLBACK') = (rollback_of_deployment_id IS NOT NULL))`, the five indexes), plus these **† additions beyond DATABASE §5.2**, each needed by this milestone:
- `failure_reason text NULL` (the contract's 21.3 returns it; the table did not have it) with a CHECK that it is non-null for `FAILED` and null otherwise;
- `queue_item_id bigint NULL` (finding 4);
- `target_digest text NOT NULL` — SHA-256 hex over the canonical JSON of the target's `pipeline_reference` and `parameter_template` at request time (finding 9);
- `next_poll_at timestamptz NULL`, `poll_attempts integer NOT NULL DEFAULT 0 CHECK (>= 0)`, `last_polled_at timestamptz NULL` (D5).
Plus `CREATE UNIQUE INDEX uq_deployments_single_inflight ON deployments (application_id, environment) WHERE execution_status IN ('REQUESTED','AWAITING_APPROVAL','APPROVED','QUEUED','RUNNING')` — **the one-active-deployment rule is a storage guarantee, not a pre-check that races** — and a poller index on `(next_poll_at) WHERE execution_status IN ('QUEUED','RUNNING')`. A CHECK that a `RUNNING`/`SUCCEEDED` row has `external_execution_id`. Rows are never deleted. No new permission (`deployment:*` exist). Hand-reviewed, then upgraded, downgraded and upgraded against real PostgreSQL (CLAUDE.md §5).

### D5 — `OPEN-136` Execution shape: an execute task, a due-row poller, a reaper
- **`dcp.deployments.execute(deployment_id)`** on the `deployments` queue, **an id and nothing else** (SECURITY §22). It: re-authorises and re-validates (D6) *after* the claim, so a denial is recorded against a row that really started → claims `REQUESTED|APPROVED → QUEUED` (committed) → fetches a crumb and triggers **once** → persists `queue_item_id` in its own committed transaction → sets `next_poll_at` → returns. It is short (hard limit 120 s). It is enqueued **after** the request's commit; the healer covers a lost message.
- **`dcp.deployments.poll_due`** on `deployments`, beat every 10 s. It leases up to 20 rows: `SELECT … WHERE execution_status IN ('QUEUED','RUNNING') AND next_poll_at <= now() ORDER BY next_poll_at LIMIT 20 FOR UPDATE SKIP LOCKED`, sets `next_poll_at = now() + 60 s` (the lease) in the same transaction, commits, then polls each row outside the lock and writes `next_poll_at` from the outcome. **A killed worker's lease simply expires and the row is polled again; nothing re-triggers** (the trigger is only ever reached through the claim). One poll step: `QUEUED` with a queue id → `queue_item` (`waiting` stay; `started(n)` → persist `external_execution_id = n`, `QUEUED → RUNNING`, `started_at`; `cancelled` → `CANCELLED`; `gone` → D6's reconcile); `RUNNING` → `build` (`building` stay; result → D7).
- **Backoff:** a successful poll reschedules at 5 s; a `JenkinsError` on a read increments `poll_attempts`, records `last_poll_error` (**the closed reason only**, never Jenkins' words) and reschedules at `min(5 · 2^attempts, 60)` s; a success resets `poll_attempts` and clears `last_poll_error`. `last_polled_at` is written on every attempt so a page can say how stale it is. An open circuit counts as an error. These are named module constants and working defaults, not measurements.
- **Deadline:** `deadline_at = created_at + DCP_DEPLOYMENT_DEADLINE_SECONDS` (default **3 600**, bounds 60 – 21 600, validated at start-up; `.env.example` entry **and** Compose passthrough, issue 54). The clock starts at the request. A per-target deadline would need a column and a contract change and is not built (finding 8).
- **`dcp.deployments.reap`** on **`maintenance`**, every 30 s (so a saturated `deployments` queue cannot stop it): `QUEUED | RUNNING` past `deadline_at` → `FAILED / DEPLOYMENT_TIMED_OUT` with `sanitized_result.reconciliation_required = true` and `build_may_still_be_running = true` (DCP cannot stop it); `REQUESTED | APPROVED` past `deadline_at` → `FAILED / EXPIRED_BEFORE_START`; `REQUESTED | APPROVED` unclaimed for over 30 s and inside the deadline → re-enqueue `execute` (idempotent, the claim is guarded). The slot is therefore always freed.

### D6 — `OPEN-137` Trigger outcomes, reconciliation, and what is not retried
The worker's re-check, in order, after the claim: the requester exists and is enabled → still holds `deployment:create` over the row's **stored** environment and application → the application exists and is not archived → Jenkins is configured and DCP is not in demonstration mode → the target (`deployment_target_id`) exists, is not retired, is `ACTIVE` → its **current `target_digest` equals the row's** (else `TARGET_CHANGED`) → `requested_ref` still matches the target's patterns (else `REF_NOT_PERMITTED`) → D2's approval check. Any failure is a terminal `QUEUED → FAILED` with an audit row and **zero Jenkins calls**.
Outcomes (the closed `failure_reason` set, `deployments/codes.py`; `HEALTH_CHECKS_FAILED` is added by M5.5):

| Event | Row | `failure_reason` | `reconciliation_required` |
|---|---|---|---|
| Re-check refuses | `FAILED` | `PERMISSION_REVOKED`, `APPROVAL_REQUIRED`, `TARGET_VALIDATION_FAILED`, `TARGET_CHANGED`, `REF_NOT_PERMITTED`, `NOT_CONFIGURED` | no (nothing sent) |
| Trigger refused or never sent (`may_have_acted = false`: unreachable before the write, `circuit_open`, `destination_refused`) | `FAILED` | `JENKINS_UNAVAILABLE` | no |
| `auth_failed`, `crumb_rejected` | `FAILED` | `JENKINS_AUTHENTICATION` | no |
| `job_not_found` | `FAILED` | `JOB_NOT_FOUND` | no |
| `trigger_outcome_unknown` | stays `QUEUED`, no queue id | — (see below) | — |
| Queue item `cancelled` in Jenkins | `CANCELLED` | — | no |
| Pipeline `FAILURE`, `UNSTABLE`, `ABORTED`, `NOT_BUILT` | `FAILED` | `PIPELINE_FAILED`, `PIPELINE_UNSTABLE`, `PIPELINE_ABORTED`, `PIPELINE_NOT_BUILT` | no |
| Deadline | `FAILED` | `DEPLOYMENT_TIMED_OUT` | **yes** |

- **Nothing that changes state is retried** (CLAUDE.md §5). M5.1's note that M5.2 "retries the not-sent case" is **not taken**: a not-sent trigger is a terminal `JENKINS_UNAVAILABLE` and the user requests again (a new key, a new row; the one-active rule has freed the slot). Fewer moving parts, and no path that can double-trigger.
- **Reconciliation of an unknown outcome.** The poller treats a `QUEUED` row with `queue_item_id IS NULL` older than 60 s as "the trigger may have been sent" (a live worker is given that long). If the target's template has a `deployment_id` slot, a **new read-only client method `find_by_parameter(job_path, name, value)`** looks in Jenkins' queue and the job's recent builds (`tree=` queries, retried like any read) for the one carrying DCP's own `deployment_id` UUID; **found → persist the queue id or build number and carry on, never trigger again**; not found after a further 120 s → `FAILED / TRIGGER_OUTCOME_UNKNOWN`, `reconciliation_required = true`. A target **without** the slot cannot be reconciled: its row ends `FAILED / TRIGGER_OUTCOME_UNKNOWN` at 60 s, the page says so, and the target list says that its deployments cannot be reconciled. Registration is **not** changed to require the slot (existing targets, and nothing is deployable today). `QueueState("gone")` takes the same path. The parameter *name* comes from the administrator's template; the *value* is a UUID DCP generated — **no request value reaches Jenkins except the validated `ref`**. The mock gains the corresponding responses.
- **Honest limit:** a worker killed between the claim and the call also leaves a `QUEUED` row with no queue id, and that state cannot be told from "sent, no answer" — it is treated as the latter (the safe side).

### D7 — `OPEN-138` The success policy now, and the "no checks configured" result
`app/deployments/policy.py` holds one pure function, `success(pipeline_result, health) -> bool`, true only for a pipeline `SUCCESS` **and** `health.passed is True`. `UNSTABLE` is not success. Until M5.5 `health_check_config` is `{}`, so the result recorded is **explicit**: `{"policy": "all_must_pass", "configured": false, "checks": [], "passed": true}` — never a bare `{}` (issue 197a). The success policy is vacuously satisfied with nothing configured, and **the page says it in words**: "No post-deployment health checks are configured for this target; success means only that the pipeline succeeded." M5.5 fills `checks` and may turn `passed` false. **Two independent guards** (the milestone's worst failure mode, mandatory rule 8): the machine refuses `→ SUCCEEDED` without a pipeline `SUCCESS` and a passing result, **and** the schema `CHECK` refuses it without evidence; a mutation check shows each alone fails a named test.

### D8 — `OPEN-139` The request path (21.2): order, idempotency, rate limit
Order: session → `Idempotency-Key` present (`422`) → body validated (`extra="forbid"`: `application_id`, `environment` (closed enum), `ref`, `reason`) → the caller holds `deployment:create` over `(environment, application)` (`403`, audited `DEPLOYMENT_DENIED` and `AUTHZ_DENIED` as the project does — **before** anything about registration or configuration is revealed) → the application exists (`404`) → `resolve_target` (`422 not_registered`, M5.1's function, first as issue 197d says) → the ref grammar, then `ref_permitted` (`422 not_permitted`, the allowed patterns in `details`, as the contract says) → Jenkins configured and not in demonstration mode (`503 not_configured`, closed reason) → **idempotency lookup** (replay: `200`, the original, `idempotent_replay: true`, no budget spent, nothing executed) → D2's approval evaluation → `reason` (required for `production`, or when approval is required; 1 – 500 printable characters) → rate limit **10 / hour / identity / environment** (SECURITY's table; the privileged class, **fails closed** when Redis is unavailable, `Retry-After`) → insert the row and its audit in one transaction (the storage guards decide the races) → commit → enqueue `execute`.
- Key scope is `UNIQUE (requested_by, idempotency_key)`; body comparison on `(application_id, environment, ref, reason)`; a different body under the same key is `409 conflict`. Two concurrent submissions of one key: one wins, the loser's `IntegrityError` becomes a replay. A different key against a pair with an active deployment: `IntegrityError` on `uq_deployments_single_inflight` → `409 operation_in_progress`; the courtesy pre-check exists for a clean message only.
- `202`, the contract's shape, with `approval: null` (nothing pending until M5.4), the resolved target echoed (**the exact target, before and after**, PRD §4.10), `deadline_at`, `correlation_id`, `poll_after_seconds`. The digest, the template and the queue id are not in any response.
- The route carries the explicit dependency `deployment:read` as its floor and the handler asks the real question with `authorized.permits("deployment", "create", target)` (the M4.2 pattern, so the route-coverage test passes and the production/non-production split is the matcher's, not a role check). Blocked in read-only mode (`423`).

### D9 — `OPEN-140` Reads, scope, and the dashboard
- **21.1** Query: `application_id`, `environment`, `execution_status` (repeatable), `requested_by`, `kind`, `from` / `to` (bound `created_at`; omitted ⇒ the last 7 days with the same five-minute slack as §23; over 90 days or `from` after `to` ⇒ `422`), `limit` (1 – 200, default 50), `cursor` (the §5 signed cursor), newest first; an unknown parameter is `422 unknown_field`. **Scope is one SQL predicate, applied in the query:** a deployment is listed when the caller requested it **or** holds `deployment:read` over its **stored** `environment` and its `application_id` (the same two dimensions as a target; a grant naming an account or server reaches nothing — A-09), built from `authz/queries.py` as M4.6's predicates were, with a cross-check against the matcher. Out of reach is absent, never forbidden.
- **21.3** adds `commit_sha`, `external_execution_id`, `started_at`, `completed_at`, `health_check_result`, `pipeline_result`, `failure_reason`, `sanitized_result`, `last_poll_error`, `last_polled_at`, `approvals: []` (empty until M5.4), `rollback_of_deployment_id`. **`links.logs` is absent until M5.3**, and the page says logs are not available yet. **No Jenkins URL appears anywhere**: the target is shown as its job path and the build as a number. Visible to the requester, or to `deployment:read` over the stored environment and application; otherwise **`404`**, never `403`.
- **Dashboard.** `recent_deployments` becomes a real section — the ten most recent deployments that `deployment:read` reaches over the stored environment and application — 21.1's scope **without** its "or you requested it" half, because the dashboard cache is keyed by scope and not by person (the M4.6 rule; **amended in commit 1**, the plan first said "21.1's predicate"); `items: []` means "nothing you may see" and stays distinct from `not_configured` with `null` — and rides the scope-keyed cache. `schema.ts` is regenerated in the same commit (CLAUDE.md §5); the dashboard contract line is amended.

### D10 — `OPEN-141` Cancel (21.6) and the retire guard (21.12)
Cancel: the requester, or a `deployment:approve` holder over the stored environment and application, only from `REQUESTED` / `AWAITING_APPROVAL`; the machine decides, and a cancel that loses the race to a worker claim is `409 invalid_state_transition`, never a false "cancelled". Audited `DEPLOYMENT_CANCELLED`. **21.12** (retire a target) is refused `409 invalid_state_transition` while a non-terminal deployment exists for that target; the check is one query plus the storage guard that already stops two active rows. Archiving an application is already refused while it has a live target (§18.5), so no second guard is added there.

### D11 — `OPEN-142` Audit
Names are taken from the existing §28 catalogue and checked in commit 1; any missing one is added there, not invented in code. One row per transition, **in the same transaction as the transition** (a failed audit write means the transition does not happen, SECURITY §18): requested, denied, cancelled, queued (the claim), running (build number assigned), completed (every terminal state, with status and `failure_reason`). Worker rows carry `actor_id = requested_by`, `actor_label = "system:deployments-worker"` and `on_behalf_of` (mandatory rule 7), all with the deployment's `correlation_id`. Metadata holds ids, the validated `requested_ref`, the build number, `commit_sha` and closed codes (PRD §4.10 "record commit SHA, pipeline ID, requester, timestamps and result"); **`reason` is audited by length only**, never the template, the digest or any Jenkins text. Each route is registered in the M4.6 audit-completeness registry (an undeclared one fails the build).

### D12 — `OPEN-143` Frontend
A **Deployments** page at `/deployments` (list with filters and paging, every data state) and a detail page at `/deployments/:id` that polls 21.3 at `poll_after_seconds` until terminal and shows application, environment, requested ref, **commit SHA**, requester, approval status, pipeline status and result, build number, timings, the failure code with a plain sentence and the redacted diagnostics, **`last_poll_error` and how stale the last poll is**, the health-check statement of D7, rollback availability as "not available yet" (M5.5), logs as "not available yet" (M5.3), and a Cancel button while cancellable. A **Deploy** action on a target row (for a holder of `deployment:create`, hidden otherwise — advice only, the backend decides) opens a confirmation dialog restating **application, environment, pipeline reference, ref and requester**, production visibly distinct, a required reason when the policy asks, one `crypto.randomUUID()` Idempotency-Key per open, and renders `503 approval_workflow_unavailable`, `503 not_configured`, `422 not_registered`, `422 not_permitted` and `409 operation_in_progress` as their closed reasons, never a generic error. The M5.1 banner for "Jenkins not configured / demonstration mode" disables the action. The dashboard's recent-deployments list becomes real.

### D13 — `OPEN-144` How it is tested
All lifecycle tests run **in process**: the Jenkins client is mounted on the mock's WSGI app through `httpx.WSGITransport` (M5.1's layer 1), and the worker functions (`execute.run`, `poll_due`, `reap`) are called directly against the real test PostgreSQL and Redis — no broker. "Worker restart resumes without re-triggering" is a test that abandons a poller mid-lease, advances the clock past the lease and runs another, then asserts from **`/__mock/requests`** that exactly one trigger ever arrived; "duplicate requests produce one build" asserts the same. One new Compose smoke step (18j) drives the whole lifecycle over the real network path against `mock-jenkins`; it is **written in M5.2 and run only with your agreement to the smoke script's `down -v`** (issue 144) — hosted CI runs it, and the handover says which. None of this is evidence about a real Jenkins; the owner's manual run (issue 191) is still the only thing that can confirm the crumb, `Location` and parameter-lookup assumptions.

## 5. Security checklist (CLAUDE.md §4)

- [ ] No endpoint, task or client method accepts a URL, a job path, a build parameter or a command from a request (rules 1, 9); the adversarial test and a signature-inspection test of the execute and poll entry points.
- [ ] A deployment targets only a registered target; the worker re-checks the digest and the pair (rule 2).
- [ ] A production deployment needs an approval; before M5.4 it is refused at the request and again by the worker (rule 3).
- [ ] Every new route has an explicit permission dependency and `deployment:create` is evaluated on the environment; the route-coverage and audit-completeness gates are green (rule 4).
- [ ] The token appears nowhere new; no Jenkins URL, body or console text is stored or returned; canary sweep over responses, audit rows, `sanitized_result`, `last_poll_error` and logs (rule 5).
- [ ] Any failure resolving a session, scope, target, policy or credential denies (rule 6).
- [ ] Every transition names an initiating identity or a named system actor and commits with its audit row (rule 7).
- [ ] `SUCCEEDED` only after a pipeline `SUCCESS` and a recorded health result (rule 8); no success on a missing result.
- [ ] Alert payloads, build results and Jenkins output are data: only a closed set of results is mapped, and no Jenkins word reaches a column or a page (rule 10).
- [ ] Tasks carry the id and nothing else; every outbound call has a timeout; **the trigger is never retried** (CLAUDE.md §5).

## 6. Risks

- **Jenkins semantics vary by plugin set.** The parameter lookup and the queue-to-build hand-off are proven against a mock only; the lookup depends on Jenkins exposing `ParametersAction` for queue items and builds, which a real instance may not. The fallback is the honest failure, never a re-trigger. *Mitigation:* the owner's manual run (issue 191) before this is relied on.
- **The slot is held for up to an hour** by a build that was lost or a Jenkins that went quiet. Intended (one active deployment) and bounded by the deadline; the reaper frees it and says the build may still be running.
- **Production cannot be deployed until M5.4.** Fail-closed by design; the UI states it.
- **A `QUEUED` row with no queue id is ambiguous** (D6's honest limit). Safe side chosen: no second trigger.
- **Poller load.** 20 rows per 10 s tick is a working default for a single-host Compose deployment, not a measurement.
- **Windows development:** a killed worker leaves children; the lifecycle tests therefore call the functions directly and use no subprocesses.

## 7. What would change this plan

A real Jenkins that does not expose parameters on queue items (D6's reconcile becomes the honest failure for every unknown outcome); the owner choosing to build the approver in this milestone (D1, D2 reverse and M5.4's work moves in); a per-target deadline becoming a requirement (a column and a contract change); or the owner wanting a deployment-failure alert in this milestone (a producer, as M4.3 did for operations — currently deferred under `OPEN-40`'s rule that a condition ships with the thing that can fail for real).

**Not M5.2:** approve / reject (M5.4), the console endpoint and log panel (M5.3), health-check execution and rollback (M5.5), aborting a build, a deployment-failure alert producer, a per-target deadline, requiring the `deployment_id` slot at registration, a Playwright spec, seeded demo deployments.

## 8. What differed from this plan (as it happened)

*Commit 2 (the pure core and migration `0015`, 2026-10-24):*

1. **The plan's table had no `requested_reason` column**, though 21.2 takes `reason`, D8 compares it for idempotency and D11 audits its length. Added to `0015` (`text`, at most 500 characters) and to DATABASE §5.2 as a †. Found by writing the model against the contract rather than against the table.
2. **A composite foreign key was added** on `(deployment_target_id, application_id, environment)` to `deployment_targets`, with a unique constraint on `(id, application_id, environment)` added to `deployment_targets` for it to point at. The plan said the table "proves the deployment used a registered target", but nothing made the deployment's application and environment *the target's*; reads are scoped on the stored environment (D9), so a disagreeing row would be mis-scoped. Found because the first version of a schema test (`refused_by`, which checks *which* constraint refused) showed the application-delete case was being refused by a different table's key. Three tests pin it.
3. **More CHECKs than D4 listed:** a terminal row has `completed_at`; `requested_ref` is 1 – 200 characters; `pipeline_reference` obeys the job-path grammar; `commit_sha` and `target_digest` have their shapes; a reason is at most 500 characters. A value over a column's length is refused as a `DataError` before any CHECK, which the schema tests accept as the database refusing it.
4. **`deployments/store.py` (the guarded `UPDATE … RETURNING` transition statement) is not in this commit.** D3 describes it; nothing calls it until commit 4 (the request path) and commit 5 (the worker), so it lands with its first caller rather than as unused code.
5. **`tests/test_db_units.py`:** its "history tables are not created early" canary (which listed only `deployments`) is retired, as it was for `operations` and `approvals`, and `Deployment` joins the registered-model set.
6. **`downgrade` of `0015` refuses while any deployment exists** (they are the audit record, never deleted); `0014`'s and `0013`'s downgrade tests now compare against the current head instead of the literal `"0014"`.
7. **`codes.trigger_failure(reason, may_have_acted)`** returns `None` (reconcile) for *any* reason when `may_have_acted` is true, not only `trigger_outcome_unknown`: a `5xx` after the write is also ambiguous, and ending the row would free the slot while a build might be running. D6's table says the same in words; the function is now the one place it is true.

*Commit 3 (`find_by_parameter`, the mock and the deadline setting, 2026-10-24):*

8. **`find_by_parameter` is stricter than D6's sentence.** The parameter name and value are checked against closed grammars before any request (`[A-Za-z_][A-Za-z0-9_]{0,63}` and `[A-Za-z0-9-]{1,64}`); every entry of a list must be a dict with a positive integer id or number, so **a garbled list is `provider_error` and never an empty answer** ("I could not read it" must not read as "there is no build"); two matches in either list is `provider_error` (it means a double trigger, and picking one would hide it); the queue is read first and the build list only when the queue has no answer. It looks through the **50** most recent builds, a named constant (`RECENT_BUILDS`); an older build is `None`, which the caller reports honestly.
9. **The mock gained two read-only listings and a `hide_parameters` mode**, and `lose_queue_item` now also starts the build (that is what losing a queue item means). **The mock ignores `tree=`**, so it is not evidence that a real Jenkins accepts the `builds[...]{0,50}` query; that stays with the owner's manual run (issue 191).
10. **`DCP_DEPLOYMENT_DEADLINE_SECONDS`** is a setting with the bounds copied into `core/config.py` (`core` does not import a feature package); a test pins that they equal `states.MIN_` / `MAX_` / `DEFAULT_DEADLINE_SECONDS`. It is in `.env.example` and the Compose passthrough (issue 54) and **has no consumer until commit 4**. API_CONTRACTS §27's "Target policy" wording is corrected to the setting.
11. **A mutation check found a test that proved less than it said.** The "issues only GET requests" test found its match in the queue and never reached the build-list read, so making that read a `POST` did not fail it. It now runs both ways (found in the queue; reading both lists) and fails for that mutation.

*Commit 4 (the request path, reads and cancel, 2026-10-24):*

12. **The implementation was written before its integration tests this time** (commits 2 and 3 were tests first). The unit tests for the store and the approval rule, and all 156 API tests, followed it, and **nine mutation checks** then took one guard away each (the permission check, the approval refusal, the ref patterns, the visibility check, the list's scope half, the guarded `UPDATE`'s status check, the 21.12 guard, the Jenkins-configured check, the replay lookup) and each failed a named test. That is the evidence the tests bite; it is weaker than having watched each fail before the code existed.
13. **The replay lookup moved ahead of the target lookup** (plan D8 had it after the Jenkins check). A replay now returns the original whatever the target or Jenkins is now. Contract and `OPEN-139` amended.
14. **`reason` is optional in M5.2** and the "required for production or when approval is needed" rule is not built: every request it would apply to is refused first, so the branch would be unreachable and untested. It arrives with M5.4.
15. **Cancel is `REQUESTED` only.** The table allows `AWAITING_APPROVAL → CANCELLED`, but the approval row's side of a cancel is M5.4's and nothing in M5.2 creates one, so it is `409` rather than half-handled.
16. **`deployments/store.py` is complete, not minimal:** the whole guarded transition (claim, run, finish, fail, with the success and failure evidence rules) is there and unit-tested, though only cancel calls it yet; commit 5's worker is its other caller. `Origin` is imported from `app.operations.service` rather than copied.
17. **New files:** `approval.py`, `store.py`, `listing.py`, `lifecycle.py`, `deployment_schemas.py`, `deployment_router.py` (the existing `router.py` / `schemas.py` / `service.py` are the *targets'*, and are left alone except for the 21.12 guard in `service.py`). `authz/queries.py` gains `readable_deployments`.
18. **Test-data lesson:** a deployment row cannot be written for another environment than its target's (the composite key from commit 2), so scope tests register a second, development target instead of inserting a "production" row. The first version of the list-scope test also forgot that a requester always sees their own rows.
