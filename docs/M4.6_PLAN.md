## 0. What M4.6 is, and what it is not

**Is** (IMPLEMENTATION_PLAN): endpoints 23.1 – 23.2 and 24.1 – 24.3; the export task; the operations-history and audit-log pages with filters. **Acceptance (PRD §4.12):** every privileged operation traces to its initiating identity; operation history includes the result and the execution id; audit records cannot be altered through ordinary APIs. **Tests named by the plan:** a test that enumerates state-changing endpoints and asserts each produced an audit row; immutability under the app role; `AUDIT_QUERIED` written when the trail is read; export bounds enforced; no secret in any audit row (canary sweep); export audited and single-retrieval; `audit:read` restricted to Approver / Administrator.
**Is not:** audit retention or `DROP PARTITION` (`DATABASE.md` §10; runway only exists), the independently protected export destination and the non-superuser application role (M6.2, `OPEN-15`), hash-chained records (`SECURITY.md` §18 `[FUTURE]`), deployment history (M5), CSV or any export format but `jsonl`, free-text search over `sanitized_metadata`, a total-row count.
**The sentence to hold on to afterwards.** After M4.5 a person could *do* things and DCP wrote them down; after M4.6 a person can *read* what was done, scoped to what they may see, and reading it is itself written down. Like all of Phase 4 the operations history shows what stubbed providers and one sandbox run produced.

## 1. Findings that shaped the decisions

1. **An audit row has one scope dimension, not four.** It carries `environment` and a polymorphic `(target_type, target_id)` with no foreign key. `SECURITY.md` §18 says "rows are scope-filtered", but a grant scoped to `server` or `cloud_account` cannot be evaluated against most audit rows without a join DCP deliberately does not have. And many events have **no environment at all** (logins, role grants, user changes, system events). (D4)
2. **The operations list and the operation detail can disagree today.** `visible_operation` asks the matcher about the server's *current* environment label (issue 164); §17.2 says the *stored* one. A history list that picks the stored column and a detail page that picks the live label would show a row you cannot open. (D2)
3. **The export has nowhere to live.** §24.3 says the result is "retrievable once"; there is no export table, no object store (`OPEN-15` is undecided), no endpoint to ask for status or fetch the file, and the Celery tasks take an id and nothing else. (D7)
4. **`AUDIT_QUERIED` turns every page of a read into a write.** The contract is clear that reading the trail is a privileged act; the cost is one `audit_events` row per request, in the table the request is reading. (D5)
5. **The completeness test is the largest piece of work in the milestone.** There are 34 `post` / `patch` / `delete` handlers in `backend/app/**/router*.py` (counted by grep, not by walking the routing table) plus `webhook.py` and `auth/router.py`, some of which are POSTs that change nothing (`/logs/query`). Each needs a recipe that drives it. (D9)
6. **The dashboard's `recent_operations` section is waiting for exactly this scoping function** (issue 143), and flipping it is a response-shape change. (D11)
7. **The "immutability under the app role" test cannot be what its name suggests.** There is no non-superuser application role yet (M6.2); the existing tests run as a role the grants alone would not stop and rely on triggers. (D8)
8. **`AUDIT_EXPORT*` names are partly missing from the catalogue.** §24.3 names `AUDIT_EXPORTED` only; "when is it written — on request, on build, or on download?" is not said. (D7)

## 2. Decisions (recommended; need your reading)

### D1 — `OPEN-106` Scope
Built: migration `0013` (`audit_exports`); §23.1, §23.2, §24.1, §24.2, §24.3 and two additions that make §24.3 usable (D7); the export task and its expiry sweep; the stored-environment scope predicate for operations and the environment-only predicate for audit rows (D2, D4); `AUDIT_QUERIED`; the dashboard's `recent_operations` section; the completeness, immutability, canary and bounds tests; the two pages and the per-server operations tab; navigation. *Rejected:* anything in "Is not" above.

### D2 — `OPEN-107` Operations history: whose rows, on which basis
A row is listed when the caller **requested it, or** holds `operation:read` over its **stored** `operations.environment` and the target server's other dimensions (account, server id). One SQL predicate, built from the same grants by the same rules as `readable_servers` (it is that function with the environment column swapped, so there is still one matcher and the existing cross-check test gets a second column to prove). **Issue 164 is fixed in this milestone** so the list and §17.2 agree: `visible_operation` asks about the stored environment. This changes M4.2 code and is the one deliberate step outside "this milestone's new files" — it is the narrowest fix and the alternative is a list that contradicts its own detail page. §23.2 requires the server to be visible to the caller (`server:read`, else `404`, never an empty list) and then runs the same query with the server fixed. A caller with only `operation:read` and no `server:read` over a server gets that server's operations from §23.1 but `404` from §23.2 — stated, not hidden.

### D3 — `OPEN-108` Query shape for §23
Filters exactly as the contract lists; every id filter is a UUID, `execution_status`, `action_type` and `environment` are enums (`422` otherwise). `from` / `to` bound `created_at` (whatever the sort); omitted ⇒ the last 7 days; a range over 90 days ⇒ `422`. Cursor pagination with the project's signed cursor, `limit` default 50, max 200, no total. `sort` ∈ `created_at | completed_at`, default `created_at` descending. **`completed_at` is NULL while an operation is in flight, and the cursor helper carries a text key:** sorting by it orders NULLs last in both directions with an explicit sentinel in the cursor and a two-part keyset comparison; this is the piece most likely to repeat or skip a row at a page boundary, so it has a test with ties and NULLs straddling a boundary. Items carry the contract's fields **plus** `external_execution_id`, `observed_state_before` and `observed_state_after` (PRD §4.12: "includes the result and associated execution id"; all three are closed values or an opaque provider id, already on §17.2). `requested_reason`, `sanitized_result` and `parent_operation_id` stay on the detail only.

### D4 — `OPEN-109` Scope of audit rows
`audit:read` is checked against the **event's `environment`** under the same rules as everywhere (deny wins; production only when named; malformed means deny). **A grant that constrains `cloud_account`, `server` or `application` reaches no audit row** — the event does not have that dimension (A-09: a missing dimension is a denial). **An event with no environment is visible only to a grant that covers every environment** (the dimension absent, `*`, or all four named) **and names no specific account, server or application** — the seeded Administrator's shape; an Approver scoped to production does not see logins, role grants or system events. *(As agreed this paragraph said "a grant that constrains nothing (every dimension absent or `*`), which is the seeded Administrator"; building it showed the bootstrap Administrator names all four environments, so that wording would have hidden these events from the one role that can export them. The owner chose the cover-all rule on 2026-10-22.)* This is strict on purpose and is the fail-closed reading; the cost is that a production-scoped approver cannot see an `AUTHZ_DENIED` that had no environment. The predicate lives beside `readable_servers`, is cross-checked against the matcher in the same test file, and `matcher._in_scope` is read before it is written (it decides how a target with `environment=None` is matched). *Rejected:* joining each event to its target to derive more dimensions (a foreign key audit rows deliberately lack; `DATABASE.md` §15).

### D5 — `OPEN-110` `AUDIT_QUERIED`
Written by §24.1 and §24.2 in the request's own transaction, actor the caller, `target_type = 'audit'`, `environment = NULL`, outcome `SUCCESS`. Metadata is **the filter names and their id/enum values, the page size, the number returned and whether there is more** — never the rows and never a cursor. It is written for an empty result too (an empty answer is still a read). If the audit write fails the request fails (`SECURITY.md` §18). A caller refused by the permission or the scope gets the existing `AUTHZ_DENIED`, not `AUDIT_QUERIED`. The operations history (§23) is **not** audited as a read: the contract audits reading *the trail*, not the operation list, and doing the latter would multiply writes for no PRD requirement. *Accepted cost:* one row per page fetched. The audit-log page therefore never refetches on a timer or on focus.

### D6 — `OPEN-111` What §24.1 and §24.2 return
The table's columns: id, `occurred_at`, actor type, actor id, actor label, action type, target type and id, environment, correlation id, `approval_id`, outcome, **source IP and user agent** (they are part of the record `SECURITY.md` §18 lists, and an authorised reader of the trail is who they are for), and `sanitized_metadata`. Metadata is passed through `redact_value` **a second time on the way out** (the M3.2 precedent: the stored value is already redacted, and a row written before a redaction rule improved is read under the current rules). §24.1 filters as the contract lists, all closed or UUIDs. Window: omitted ⇒ last 7 days; `from` / `to` are required to look beyond 7 days; more than 90 days ⇒ `422`. Keyset on `(occurred_at, id)` descending, which is the table's primary key and index order, so the 90-day bound is also what keeps the partitions scanned bounded (checked by `EXPLAIN`, see §4).

### D7 — `OPEN-112` Export: storage, retrieval, audit
**Storage: a table, `audit_exports`** (migration `0013`): id, `requested_by`, `from_at`, `to_at`, `format` (`jsonl` only, a CHECK), `status` (`QUEUED | RUNNING | READY | FAILED | RETRIEVED | EXPIRED`), `failure_code` (closed), `row_count`, `size_bytes`, `sha256`, `content bytea` (NULL unless `READY`), `idempotency_key`, `created_at`, `completed_at`, `retrieved_at`, `expires_at`. CHECKs: `READY` ⇔ content present; `RETRIEVED` / `EXPIRED` ⇒ content NULL; `UNIQUE (requested_by, idempotency_key)`; a partial unique index making **one active export per requester** a storage guarantee. PostgreSQL is the only store shared by the API and the worker that is already durable; Redis would hold tens of MiB in memory, a container volume is not shared or persistent, and an object store is `OPEN-15`, undecided.
**Bounds (design budgets, not measurements):** window ≤ 31 days (contract); ≤ 100 000 rows and ≤ 64 MiB. Over either ⇒ the export ends `FAILED` / `export_too_large` — **never truncated silently** — and the requester narrows the window.
**The task** `dcp.audit.export(export_id)` on `maintenance` takes the id and nothing else. It **re-resolves the requester's grants**, re-checks `audit:read` and `admin:integrations` (a requester demoted after asking gets a `FAILED` / `requester_not_authorised` export and no data), applies the D4 predicate, reads in keyset chunks, redacts again, writes `jsonl`, and stores the hash. It is the same arithmetic as §24.1 and shares its query builder.
**Endpoints added to the contract** (the plan cannot be implemented without them): **24.4** `GET /audit-events/exports/{export_id}` — status, counts, hash, expiry; **24.5** `GET /audit-events/exports/{export_id}/download` — the file, **once**: a guarded `UPDATE … SET status='RETRIEVED', retrieved_at=now(), content=NULL WHERE id=:id AND requested_by=:caller AND status='READY' AND expires_at>now() RETURNING content`; a second call, a stranger's call and an expired call are `404`/`409` and never a file. Both require the same two permissions as §24.3 and are visible to the requester only. If the transfer then fails the export is spent and the requester asks again — stated in the response and the UI.
**Audit:** `AUDIT_EXPORT_REQUESTED` (the request, with the window), `AUDIT_EXPORTED` (**the download — the moment data leaves**, with row count, size and hash, and never the content), `AUDIT_EXPORT_FAILED` (system actor, on behalf of the requester, with the closed code). §24.3's single name `AUDIT_EXPORTED` is kept for the act that matters. Unretrieved `READY` exports expire after 24 hours (a sweep in the existing reaper nulls `content`, sets `EXPIRED`, audited by `system:audit-export-sweeper`).

### D8 — `OPEN-113` What "immutable" will and will not be shown to mean
Three claims, each tested: (a) **no ordinary API alters or deletes an event** — a test walks the live routing table and asserts every path under `/audit-events` accepts `GET`, plus the one `POST` that is the export request, and `PATCH` / `PUT` / `DELETE` are `405`; (b) **the database refuses, for the role the application uses** — an `UPDATE`, `DELETE`, `TRUNCATE` and a partition `DETACH` through the application's own engine are each refused; (c) the existing trigger tests stay. **What it does not show:** that a least-privilege role would refuse the same. The application connects as a superuser or owner today; the separate role is M6.2. The test says so in its docstring and `PROGRESS.md` says so in words.

### D9 — `OPEN-114` The completeness test
The test builds the list from the **live routing table** (the walk `test_route_coverage.py` already does, whose own self-test guards against it finding zero routes) and requires every non-`GET` route to have an entry in a registry with one of three kinds: **audited** (the action types it must write), **no state change** (a `POST` that only reads, with the reason: `/logs/query` and similar), or **own audit** (login, logout, the webhook, whose events are written by their own code and tested elsewhere — named, with the test that covers them). A route with no entry fails the build, which is the point: a new endpoint forces a decision. For each *audited* entry the test **drives the route** with the existing integration helpers and asserts, from the database, an event with the registered action type, the caller as actor, and the request's correlation id. A route that cannot be driven in a test (it needs a real provider) is listed in a visible "not driven" set with the reason, and `PROGRESS.md` states how many routes that is. One representative route also proves the converse of rule 10: a forced failure of the audit insert fails the whole request and leaves the state unchanged. **Mutation check:** an `audit.record` removed from one handler must fail a named test.

### D10 — `OPEN-115` The secret canary sweep
Plants the project's canary values (the helper the logs and notifications tests use, located in commit 2) in the inputs of the privileged paths that take credential-shaped data — a cloud account's `credential_reference`, a notification channel's secret reference, a webhook secret, a rejecter's reason, a query's filters — then reads **every column of every `audit_events` row written** and the **export file** and fails on any canary substring. Also asserts `AUDIT_QUERIED` metadata holds no row content.

### D11 — `OPEN-116` The dashboard's `recent_operations`
Flipped from `not_configured` to a real section: the ten most recent operations that `operation:read` reaches (D2's predicate, *without* the requester half — see §8 item 7) (id, action, target, environment, execution status, requester, `created_at`). An empty list is `ok` with `items: []`, distinct from `not_configured` with `null`, as `RecentActivitySection` already says. It rides the existing scope-keyed Redis cache, so a change shows after the cache's TTL (`cache_ttl_seconds` in the response already says so). `recent_deployments` stays `not_configured` (M5). `schema.ts` regenerated; issue 143 closed. If you would rather not change the dashboard's contract in this milestone, drop D11 and issue 143 stays open — nothing else here depends on it.

### D12 — `OPEN-117` Frontend
**Operations** (`/operations`): filters (status, action, environment, server, date range, "mine"; `requested_by` by UUID in the URL only — no user directory exists, `OPEN-44`), a table whose rows open the existing `/operations/:id`, cursor paging, honest empty / error / loading states; and a per-server tab on the server page using §23.2. **Audit log** (`/audit`, shown in the navigation to holders of the advisory `audit:read`): filters, table, a detail panel (§24.2) with metadata rendered as **text**, never HTML; no automatic refresh (D5); for holders of `admin:integrations`, an *Export* dialog that states the 31-day and one-time-download rules, shows status (§24.4) and offers one download button. The backend refuses anything the page hides. vitest for: filters sent as typed, paging, empty versus unavailable, metadata containing markup rendered inert, the export dialog's states, the download button disabled after one use, axe on the dialogs. The Playwright suite is not extended (as in M4.5).

## 5. Security checklist

- Reading the audit trail needs `audit:read` **and** scope, applied **inside the SQL** (rows outside it are never fetched, counted or paged over); an unknown or out-of-scope id is `404`, never `403`.
- Every read of the trail writes `AUDIT_QUERIED` in its own transaction; a failed write fails the read.
- No audit event can be changed by any route; the database refuses for the application's role; what that does not prove is written down.
- The export is bounded by window, rows and bytes; refuses rather than truncates; re-authorises in the worker from the id alone; can be downloaded once, by its requester; and is audited at the moment data leaves.
- No secret in any audit row or export: metadata is redacted on write and again on read; a canary sweep covers every column.
- The task receives an id. No credential, query text or URL travels through the broker.
- Filters are enums and UUIDs; there is no free-text search and no user-supplied sort expression.
- Every state-changing route has a declared audit behaviour, and a new one without it fails the build.

## 6. Risks

- **Strict scope on audit rows (D4)** hides no-environment events from everyone but an unrestricted reader. Mitigation: stated; loosening it is a one-line predicate change with its cross-check test.
- **Read amplification (D5):** one audit row per page. Mitigation: no auto-refresh, `ReadBudget` rate limit on the two routes, and the volume is visible in the trail.
- **The completeness test's size (D9).** It could take as long as everything else together. Mitigation: it is commit 5 on its own, the registry is the contract (a route can be honestly listed "not driven"), and I will report the count rather than round it up.
- **A cursor with NULLs (D3)** is where a page boundary repeats or drops a row. Mitigation: the dedicated tie-and-NULL test, and the same shape as the logs cursor that already survived a real Loki.
- **Export in `bytea` (D7)** costs memory in the worker and rows in PostgreSQL. Mitigation: the caps, the 24-hour expiry, and an upgrade path to an object store when `OPEN-15` decides one.
- **Touching M4.2 code (D2).** `visible_operation` changes; the existing operation tests are the proof the rest did not move.
- **Over-claiming.** After M4.6 the *audit and history* are proven against the test database and stubbed providers, with one sandbox run behind M4.5. Nothing here is evidence about production AWS, and "immutable" means "refused by triggers", not "unreachable by a database superuser".

## 7. What would change this plan

If you want §24.3 to follow the contract literally (no 24.4 / 24.5), there is no way to retrieve the result and D7 has to choose a delivery channel (a signed link needs a store; email is a new outbound surface) — I would rather add two read endpoints. If audit rows should be visible to a production-scoped approver even without an environment, D4 gains a second rule and a decision about which event types count as "production-relevant". If you want the operations list audited as a read, D5 grows by one write per request. If you want the dashboard untouched, drop D11.

## 8. What differed (commit 2, written as it happened)

1. **D4's rule for events with no environment was changed before it was built, at the owner's choice.** The agreed text said such events are visible "only to a grant that constrains nothing, which is the seeded Administrator". Reading `matcher._in_scope` and the bootstrap CLI showed the seeded Administrator's scope *names* all four environments (rule 4), so the literal rule would have hidden logins and role grants from the one role that can read the trail and export it. Three options were put to the owner, who chose the "cover-all" rule (`matcher.permits_environmentless`): such events are reached by a grant whose environment dimension is absent, `*`, or all four environments, and that names no specific account, server or application. Contracts, SECURITY, DATABASE, ARCHITECTURE `OPEN-109` and TESTING were updated in this commit.
2. **The issue-164 fix reaches one more place than the plan said.** `visible_operation` and the cancel path's `operation:approve` check both read the server's current label; both now use `operation_target(operation, server)` (the stored environment). A consequence in existing tests: an approver scoped to a re-labelled server's *new* environment now gets `404`, not `403`, when deciding the old operation, because they cannot see it (`test_a_stored_environment_not_the_servers_current_label_decides_scope` was changed accordingly and a new test pins the read side).
3. **A gap in D7, found while writing the schema, to be closed in commit 4.** `uq_audit_exports_one_active_per_requester` means a worker that dies between `QUEUED`/`RUNNING` and a result would leave that requester unable to ever ask again. Commit 4's sweep must therefore also fail a stale `QUEUED` / `RUNNING` export (`internal_error`), and the contract in `API_CONTRACTS.md` §24.3 – §24.5 will say so then.
4. **Shared keyset helpers.** `core/pagination.py` gained `keyset_order` / `keyset_after` / `cursor_key` (rows with no value sort last in both directions; a cursor that is signed but unusable is `422 invalid_cursor`, not a crash) and `core/window.py` holds the one window rule; both endpoints' builders use them.
5. **What commit 2 does not contain:** routers, view models, `AUDIT_QUERIED`, the second redaction, the dashboard section, the export task — commits 3 and 4. The builders are tested against real rows but nothing serves them yet.

## 9. What differed (commit 3, written as it happened)

6. **The dashboard section is scope-only, not "scope or your own".** D11 said "by the D2 predicate", which includes the requester half. The dashboard rides a cache keyed by scope, not by person, so a row visible to one caller only would be served to everyone sharing that scope. The section therefore uses `readable_operations` alone (plus the dashboard's own server filters). Every seeded role has `operation:read`, so this loses nothing today.
7. **The dashboard cache key now digests `operation:read` grants as well as `server:read`.** It digested `server:read` only, which was right while every section was scoped by it; `recent_operations` is not, and two callers who read the same servers but different operations would have shared an entry. **Observed, not changed:** the alerts section is scoped by `alert:read`, which the key still ignores — a pre-existing gap of the same kind, to be recorded in `PROGRESS.md` as a known issue rather than widened here.
8. **`AUDIT_QUERIED` is committed explicitly before the page is returned**, not left to the session dependency, so that a failed audit write really does fail the read (the dependency commits after the handler has built its response). A 24.2 request for an event that is unknown or out of scope is `404` and writes nothing — nothing was read — which means probing for event ids leaves no row; the contract says exactly this and it is stated here so it is a known property and not a surprise.
9. **23.1 versus 23.2 without `server:read`** is specified (API_CONTRACTS §23) but not testable end to end: every seeded role that holds `operation:read` also holds `server:read`, and custom roles cannot be created through the API. The two checks are separate in code (`readable_operations` for 23.1, `permits("server", "read")` for 23.2) and the second is tested for a scoped caller (`404` for a server outside scope).
10. **The frontend is untouched apart from `schema.ts`.** The dashboard still renders `recent_operations` through the generic data-state banner (it type-checks against the regenerated types); the list UI is commit 6.

## 10. What differed (commit 4, written as it happened)

11. **The sweep is its own beat entry, not part of the operations reaper.** `dcp.audit.sweep_exports`, every 60 s on `maintenance`. The reaper is operations code (`execute.reap`); adding exports to it would have mixed two unrelated lifecycles in one function. API_CONTRACTS §24.3 – §24.5 says so.
12. **The build reads in pages of 200**, the read query's own ceiling (§5), not the 500 first written; the memory bound is the 64 MiB budget, not the page size. The first test run found the 500 (the builder refused it with `422` and the build ended `internal_error`).
13. **A build that loses to the sweep stores nothing** (`superseded`), and a build that finds its row already claimed does nothing (`not_queued`), so a redelivered task is harmless.
14. **Audit rows for the system's part use `actor_type = SYSTEM` with no `actor_id`** and the requester in `on_behalf_of`, because `ck_audit_events_actor_attribution` makes a `USER` actor carry an id and the approval sweeper's older convention (a requester id under a `system:` label) would make an export look as though the requester did it.
15. **Tests use one window per test.** Audit rows are never deleted and the database is shared, so each test's events sit in a minute-wide slot an hour or more in the past that no other test uses.

## 11. What differed (commit 5, written as it happened)

16. **The database does not refuse a partition `DETACH`, so D8's claim (b) was too strong and is reduced.** The plan said the triggers refuse `UPDATE`, `DELETE`, `TRUNCATE` and a partition detach. The first three are refused and are now shown through both of the application's engines. Detach is not: retention is *designed* as export, verify, `DROP PARTITION`, and the application role owns the table. The claim is dropped from `OPEN-113`, SECURITY §18 and TESTING; a **strict `xfail`** records the refusal M6.2 should bring and turns red when it does; and a source gate shows no application code issues anything but an `INSERT` against the trail.
17. **The canary sweep is two claims, not one.** The plan said no free text reaches an audit row. Planting canaries showed two fields are recorded by design: the incident switch's required reason (SECURITY §27) and an inventory edit's before-and-after values. The sweep therefore asserts that a reason on an operation request or rejection and a secret channel destination are **absent**, and that a secret-shaped value typed into the two recorded fields is **masked**. The earlier, stronger claim would have forced removing deliberate audit content.
18. **28 routes are driven, 8 are covered by named tests elsewhere, 2 are read-only queries, 1 is the public webhook.** The eight need a stubbed AWS layer (`cloud-accounts` register / edit / verify / sync, `connectivity-check`) or a seeded alert and its delivery (acknowledge, assign, retry). The registry checks each claim by finding the named test and the action in its source, and pins the counts so the "driven here" set cannot shrink unnoticed.
19. **A converse test:** a failed audit write fails the request and leaves the state unchanged (`POST …/services` with the writer refusing; the service is not registered).
20. **Mutation checks, each seen failing a named test, files restored byte-identical:** the audit row removed from `DELETE …/services/{name}` (the completeness test for that route); the `status = 'READY'` guard removed from the download statement (three tests, including the blocked-second-session one); the requester's re-authorisation removed from the build (demoted and disabled requesters); an operation's reason added to its audit metadata (the sweep). From commit 3: redaction on read, `AUDIT_QUERIED`, and the audit scope predicate.

## 12. What differed (commit 6, written as it happened)

21. **The audit log's detail panel shows the event the list already holds; it does not call 24.2.** Each call to 24.2 writes an `AUDIT_QUERIED` row, so opening ten details would have written ten rows to learn nothing new. The client has no `readAuditEvent` function at all, which is the stronger form of "the page does not ask twice". The route 24.2 stays for other clients.
22. **Both filter forms apply on a button, not on every change.** The alert list refetches as you type; this page must not, because every audit search is itself recorded, and a half-typed date would be a search. The operations page does the same for consistency.
23. **The Operations and Audit log links and the per-server Operations button are advisory**, from `operation:read` and `audit:read` in the session's permission list, like every other nav decision; the backend answers `403`/`404` on its own account. `audit:read` is Approver and Administrator only, so a Viewer sees neither link.
24. **The dashboard now lists its recent operations** (the generic banner would have shown a bare "Collected" for a real list); `[]` reads "No operations within your access scope", and `null` still reads as not configured.
25. **What was not done:** the Playwright suite is not extended (as in M4.5), and **the new pages have not been looked at in a real browser against a running stack** — they are covered by vitest (537 tests across 38 files, axe on the open detail panel and the open export dialog) and compile into the production bundle, which is less than seeing them.

## 13. What differed (commit 7, written as it happened)

26. **A default window that ended exactly at "now" was fragile, and a full run found it.** The first full integration run after commit 6 failed five `test_audit_api` tests that passed alone and in the run before. The window's end (the application's clock) was compared with `occurred_at` (the database's clock, in a container); a database clock a few tens of milliseconds ahead hides an event read a moment after it was written. An omitted `to` now reaches five minutes past now (`CLOCK_SLACK`); a stated `to` is taken exactly, and the slack is added after the range is validated so it cannot trip the 7- or 90-day rules. The measured skew when checked afterwards was 0.1 s, the other way — so this is an inference from the failure pattern, not a reproduced skew, and is stated as such.
27. **Two earlier `check-all` failures were my own tests leaving rows behind** (`application_servers` associations and notification channels from the completeness test, which other suites count). The completeness fixture now removes what it creates.
