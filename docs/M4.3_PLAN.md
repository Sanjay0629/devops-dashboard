## 0. What M4.3 is, and what it is not

**Is** (IMPLEMENTATION_PLAN): a `boto3` adapter with role-based credentials; invocation of the **registered SSM document** with typed parameters; `CommandId` persisted before polling (already done by M4.2's executor); polling with backoff; a verification read; throttling honoured via `retry_after`; `DescribeInstanceInformation` connectivity; inventory sync; error-class mapping. Plus what earlier milestones moved here: §14.8, §26.2 – §26.6, resume from the persisted handle (`OPEN-70`), the operation-failure alert (issue 137).
**Acceptance:** a restart on a non-production test instance succeeds and is verified; a throttled response backs off instead of hammering; a permission error surfaces as a configuration problem with actionable text.
**Is not:** the Azure adapter (M4.4), the approval workflow (M4.5), history and audit APIs (M4.6), a restricted agent (`OPEN-05`), a cloud-accounts admin page (D14), hybrid `mi-…` hosts (issue 130).

**The sentence to hold on to afterwards, and the limit of this environment.** This session has no AWS account, no credential, and the `aws-mcp` server failed to connect. M4.3 will therefore be **built and proven against a stubbed AWS layer only**. The acceptance criterion "a restart on a real instance succeeded and was verified" **cannot be claimed by this milestone**; it becomes true only when you run the documented real-integration check (D13) against a non-production account and the dated result is recorded in `PROGRESS.md`. Until then every status line says "never run against AWS".

## 1. Findings that shaped the decisions

1. **The registry factory takes no arguments** (`Callable[[], ProviderAdapter]`), and `ServerRef` carries no credential reference, so an adapter has no way to learn which role to assume for an account. (D3)
2. **`list_managed_services(ref)` has no unit name.** SSM has no "list unit states" API; the only way to read a unit is to run the registered document with `Action=status` and a unit name. The M4.2 executor only ever uses the registered target unit. (D3)
3. **Every read is a `SendCommand`.** There is no native read path for service state, so each pre-flight and each of the up-to-three verification reads is a Run Command round trip of seconds. IAM cannot distinguish a `status` invocation from a `restart` (no parameter condition key), so the **document** is the only read/write boundary. (D4, D6)
4. **boto3's own retries would break the "never blind-retry a write" rule.** A timeout after SSM accepted a `SendCommand`, retried by botocore, runs the action twice. (D5)
5. **`ListCommands` cannot filter by `Comment`**, so finding an execution whose handle was never recorded means listing recent commands for the instance and matching client-side. That is bounded and read-only, but it is a new adapter capability. (D7)
6. **"The role is verified to deny `AWS-RunShellScript`" cannot be probed at runtime without risk.** The only runtime probe is to attempt a `SendCommand` with that document, which, if the Deny were missing, would *run a shell*. `iam:SimulatePrincipalPolicy` needs a permission the execution role should not hold. (D10)
7. **`ON_PREM` / `OTHER` / `AZURE` accounts have no adapter**, and §26.3 would let an administrator register an account that can never be verified. (D10)
8. **There is no way to register a cloud account today** (only the seeded `ON_PREM` one). The first real account needs §26.3. (D10)
9. **`OPEN-06` (production secret store) looks like an M4.3 blocker and is not**: role-based credentials need no stored secret, so no Secrets Manager backend is required. (D2)
10. **`OPEN-23` (who owns the sandbox) is unassigned** and gates the only real test. (D13)

## 2. Decisions (closed, recommended option taken)

### D1 — `OPEN-78` Scope
In: the `AwsSsmAdapter` (`app/providers/aws/`), registry wiring, the reviewed SSM document and IAM policy as repository artifacts (`infra/aws/`), resume from the handle, §14.8, §26.2 – §26.6, per-account §26.1 rows, the operation-failure alert, a connectivity button. Out: see §0 and D14. *Rejected:* splitting resume or the alert into a separate milestone — both were explicitly handed to M4.3 by M4.2.

### D2 — `OPEN-79` Identity: role ARN only, no stored secret
- `cloud_accounts.credential_reference` for an AWS account is an **IAM role ARN** (`arn:aws:iam::<12 digits>:role/<name>`), and its account id **must equal** `account_reference`. A `secretstore://` or `env://` reference is `422` for AWS in M4.3.
- DCP's ambient identity (instance / task role, boto3's default chain) calls `sts:AssumeRole`; the session name is `dcp-<operation id>` for operations and `dcp-read` otherwise, so CloudTrail attributes each call. No external id (the SECURITY §8 recommendation is noted, not built).
- **No static keys, enforced:** the factory refuses (`NotConfigured`, `static_credentials_present`) when `AWS_ACCESS_KEY_ID` or `AWS_SECRET_ACCESS_KEY` is in the process environment, and no code path takes a key from settings or the database.
- Temporary credentials are cached in memory per role ARN until five minutes before expiry; an `AuthenticationError` triggers **one** forced re-assume (SECURITY §9, ARCHITECTURE §10.2), then terminal.
- **`OPEN-06` stays open and is narrowed:** M4.3 needs no secret from a store, so no AWS Secrets Manager backend is built. *Rejected:* building one "for later" (a credential store with no consumer).

### D3 — `OPEN-80` Two interface changes (the contract amendment to read)
1. `ServerRef` gains `credential_reference: str | None` (the role ARN; **not a secret**, shape-checked like its neighbours). It is built from the stored account row at the same sites that already build a `ServerRef` (the executor, the request path, and the new §14.8 / sync callers). The factory signature does not change.
2. `list_managed_services(ref)` becomes `list_managed_services(ref, service: ServiceRef)` and returns the snapshot of that registered unit. `ServiceRef` is already in the signature test's closed type set, so `test_signatures.py` needs no loosening and a command still has nowhere to travel. The method keeps its name to avoid a rename across the demo adapter, the test fakes and the executor; its docstring says "the registered unit asked about".
*Rejected:* a host-side managed-unit file the document would read (a fourth allowlist on every host, deployed by someone else); a free-form unit list parameter (violates the closed-type rule).

### D4 — `OPEN-81` The SSM document is security-critical code
`infra/aws/ssm/DCP-ServiceControl.json`, schema 2.2, one `runShellScript` step:
- Parameters `Action` (`allowedValues`: `start`, `stop`, `restart`, `status`) and `UnitName` (`allowedPattern` equal to `UNIT_NAME`), both with **`interpolationType: ENV_VAR`**, so the values arrive as `$SSM_Action` / `$SSM_UnitName` data and are never spliced into the script text (AWS documents this as the injection defence; it needs a recent SSM Agent — see risks).
- The script **re-validates both** (`case` on the action, an anchored regex on the unit) and exits non-zero on any mismatch, then runs a fixed argv per action (`systemctl restart -- "$unit"`); nothing is concatenated. `status` prints exactly one token, the unit's `ActiveState`.
- The adapter sends `InstanceIds=[one id]` (never `Targets`), `DocumentName` as a code constant, `DocumentVersion` from a new setting `DCP_AWS_SSM_DOCUMENT_VERSION` (digits, so an edit in AWS changes nothing until DCP is told), `TimeoutSeconds` bounded, and `Comment = dcp-op-<operation uuid>` (a typed value). Output is parsed to the closed `ServiceState` set and **never stored or returned**.
- The document is reviewed by reading, version-controlled, and covered by tests that parse the JSON: parameters have the constraints above, there is exactly one step, the script contains no `{{ }}` interpolation and no `eval`, `sh -c`, `bash -c` or backtick.
- *Not verified here:* the document has never been created in AWS or run on an instance.

### D5 — `OPEN-82` Timeouts, retries and the error table
- **Two clients per assumed session.** Reads: botocore `adaptive` retries, max 5 attempts. Writes (`SendCommand`): `max_attempts = 1`, so botocore can never repeat an invoke. Connect 3 s, read 10 s for API-side calls; the worker's invoke is bounded at 30 s total (ARCHITECTURE §10.1). No `endpoint_url` setting exists anywhere; regions are checked against the account's allowed regions and a pattern.
- **`Throttled` on a write is retried inside `_submit`** (it was refused before acting, ARCHITECTURE §10.2): honour `retry_after`, else full-jitter exponential backoff, at most 3 attempts and never past the 30 s invoke bound or the operation deadline. Every other write error is **not** retried.
- Closed mapping (botocore error code to taxonomy class): `ThrottlingException`, `TooManyRequestsException`, `RequestLimitExceeded` → `Throttled`; `ExpiredToken*`, `InvalidClientTokenId`, `UnrecognizedClientException`, `SignatureDoesNotMatch` → `AuthenticationError`; `AccessDenied*`, `UnauthorizedOperation` (and a failed `AssumeRole`) → `AuthorizationError`; `InvalidInstanceId`, `InvalidDocument`, `InvalidCommandId` → `NotFound`; `ReadTimeout` / `ConnectTimeout` → `Timeout`; `ServiceUnavailable`, 5xx, `EndpointConnectionError` → `ProviderUnavailable`; invocation status `Failed` / `Cancelled` / `TimedOut` / `DeliveryTimedOut` / `Undeliverable` → the adapter's `ExecutionStatus` states; anything unmapped → `ProviderUnavailable` with `detail_code = unmapped_error`. Provider text is never copied; only the closed `detail_code` survives.
- `AuthorizationError` carries actionable `detail_code`s (`assume_role_denied`, `send_command_denied`, `document_not_found`, `instance_not_managed`) so the UI can say what to fix (PRD §4.11).

### D6 — `OPEN-83` Capabilities (the AWS column of §7.2, made literal)
`inventory_sync` supported; `connectivity_check` supported; `start`, `stop`, `restart`, `status` supported; **`logs_tail` `not_configured`** (the document has no such action and §16.7 serves logs from Loki — "we have not set it up", not "the provider cannot"); `async_handle` true; `concurrency` `account_throttled`; `latency` `seconds`. A test pins this column against §7.2.

### D7 — `OPEN-84` Resume from the persisted handle (closes the `OPEN-70` deferral)
- **Migration `0011`:** `operations.heartbeat_at timestamptz NULL`, hand-reviewed. The worker writes it with every poll.
- The healer in `reap` also finds `RUNNING` rows **with a recorded handle**, a stale heartbeat (> 30 s, a working default) and a deadline in the future, and enqueues `dcp.operations.resume(operation_id)` (id only). The resumer takes over with a guarded compare-and-set on the old heartbeat (exactly one wins), re-runs the same worker checks as `_prepare` (permission, approval, account, target) **without** the pre-flight read, then polls from the handle, verifies and finalises. It never calls `execute_operation`.
- **A `RUNNING` row without a handle is not resumed or retried**: it stays `TIMED_OUT` / `DEADLINE_EXCEEDED` with `reconciliation_required`, exactly as in M4.2. Finding the command by `ListCommands` + `Comment` (finding 5) is **not built**: it is a recovery tool for a person, recorded as a known issue with the design written down.
- The reaper's rule is unchanged: it never calls a provider.

### D8 — `OPEN-85` Verification stays the same read
Verification remains a provider read (`OPEN-72`): after `COMPLETED`, up to three `status` invocations, two seconds apart. An independent read (issue 141) is **not built**; Prometheus stays the live display beside it. Recorded as accepted: the verifier is the same provider and the same document that acted.

### D9 — `OPEN-86` §14.8 connectivity check
`POST /api/v1/servers/{server_id}/connectivity-check`, permission `server:write`, read-only-mode applies. Scope-visible server (`404` otherwise), account `ACTIVE`, adapter resolved (`503 not_configured` for demonstration mode or no adapter, `422 unsupported_operation` otherwise), then `DescribeInstanceInformation` for that one instance through a worker thread with a 10 s bound. Response `{reachable, checked_at, provider_status, data_state, message}`; `reachable` is `PingStatus == Online`, and a server absent from SSM is `reachable: false` with `provider_status = not_registered_with_ssm`, **not** an error. Rate limit 10 / min per server. Audit `SERVER_CONNECTIVITY_CHECKED`. **It changes nothing about the server:** `agent_status`, `status` and `last_seen_at` stay owned by the Prometheus probe and the sweep (`OPEN-30`); a second source writing them would make the pages disagree.

### D10 — `OPEN-87` Cloud accounts §26.2 – §26.6 and the §26.1 rows
- **§26.2** list (cursor pagination, `admin:integrations`), never returns a reference's value beyond what §26.3 describes (`credential_reference` is a role ARN, shown with a fingerprint and `last_rotated_at` as the contract says).
- **§26.3** registers **`AWS` accounts only**; `AZURE` is `422 no_adapter_for_provider` until M4.4, `ON_PREM` / `OTHER` have none (`OPEN-62`). The body is the contract's; the ARN rules are D2; `region_configuration` is `allowed_regions` (pattern-checked) plus a `default_region` inside it. A secret-shaped value is `422 credentials_must_be_stored_in_secret_manager` and is not echoed.
- **§26.4** edits `display_name`, `region_configuration`, `credential_reference` and `status` (`ACTIVE` ↔ `DISABLED`; `ERROR` is not settable). `DISABLED` is already enforced by the request gate and the worker; this adds the route and the audit (`CLOUD_ACCOUNT_DISABLED`).
- **Region allowlist enforced in the worker:** `_prepare` refuses (`TARGET_VALIDATION_FAILED`) when the server's region is not in the account's `allowed_regions` (provider-neutral code, PRD §4.11 "restrict operations to authorized … regions").
- **§26.5 verify:** `AssumeRole`, `DescribeInstanceInformation` (one page), `DescribeDocument` for `DCP-ServiceControl` at the configured version. 15 s bound. Reports `permissions_ok` and `missing_permissions[]` for **only what can be probed read-only**; `ssm:SendCommand` is reported as `not_probed` rather than guessed. The result is cached in Redis (1 h) for §26.1. Audit `CLOUD_ACCOUNT_VERIFIED`.
- **The deny of `AWS-RunShellScript` / `AWS-RunPowerShellScript` is verified offline, not at runtime** (finding 6): (a) unit tests parse the committed `infra/aws/iam-execution-policy.json` and assert an explicit Deny on both documents, `ssm:SendCommand` allowed only on the one document ARN and on instances with `ssm:resourceTag/DcpManaged = true`, no wildcard action, no `iam:*`, `sts:*` or `Authorization`-like action; (b) `scripts/verify_aws_role.py` runs `iam:SimulatePrincipalPolicy` for an operator holding that permission, as part of the manual check. A runtime shell attempt is **never** made.
- **§26.1 gets one row per AWS account**, decided by the cached §26.5 result: none yet → `degraded` / `not_verified_yet` (unproven is not `ok`, the M3.4 channel precedent); a good result → `ok` with `last_success_at`; a failed one → `unavailable` with the closed reason; `DISABLED` → `not_configured` / `account_disabled`. No live AWS call on a status-page poll.

### D11 — `OPEN-88` §26.6 inventory sync reconciles, it does not discover
`202` plus a task id, a Postgres advisory lock per account (`409 operation_in_progress` while one runs), task `dcp.cloud.sync_account(account_id)` on the `integrations` queue. For the account's registered, non-retired `AWS_SSM` servers it calls `DescribeInstanceInformation` in batches of 50 and updates descriptive facts (`os_version`, `private_ip`, `provider_metadata.ssm`) validated by the same patterns registration uses, counts instances SSM does not know, and sets `last_sync_at` / `last_sync_error` (a closed code). It **never registers a server, never changes `environment`, `status`, `management_method` or the account**: environment is the authorisation boundary and is set by a person, never derived from a provider tag. Unregistered managed instances are *counted* (and the count goes in the audit metadata `CLOUD_ACCOUNT_SYNCED`), not created. *Rejected:* auto-registration (a tag would place a host in an environment).

### D12 — `OPEN-89` The operation-failure alert (issue 137, `OPEN-40`)
Now that a failure can be real: the executor, in the transaction that finalises an operation as `FAILED` or `TIMED_OUT`, fires a `source = DCP_OPERATION` alert `OperationFailed` about the target server (severity `warning`, `dedup_key` over the service id) through the existing shared `store.fire()`; a later `SUCCEEDED` operation on the same target resolves it in its own finalising transaction (the source resolves, `OPEN-44`). Refusals before any provider call (permission revoked, approval required) do **not** alert — they are denials, not operational failures. §26.1's alerts-coverage text and the alert list stop saying this condition is "not produced yet". If `store.fire()` cannot be called from the executor's synchronous session without a change to ingestion's isolation rules, the commit is **deferred, not forced**, and issue 137 stays open with the reason.

### D13 — `OPEN-90` Tests, the new dependency, and the sandbox (closes `OPEN-23`)
- **Dependency (TECH_STACK §10):** `boto3` runtime. It is already the approved SDK (§3, §6.2). Rungs 1 – 3 fail: SigV4 signing and STS credential refresh are not a few lines. Alternatives rejected: `aioboto3` (the interface is synchronous by `OPEN-58`), raw `httpx` plus hand-written SigV4 (a signing implementation is the one thing not to write), `moto` (a large dev dependency; its SSM fidelity is weaker than the error matrix needs). mypy treats `boto3` / `botocore` as untyped via a narrow override; the adapter talks to a small `Protocol` of the six client methods it uses.
- **Mocking:** `botocore.stub.Stubber` (part of botocore, no new package) gives exact error codes, so the whole matrix — success, throttle with and without `retry_after`, auth error, authorisation error, not found, timeout, partial failure, unavailable — is asserted at the botocore boundary, not against a hand-rolled fake. The existing conformance harness runs against the AWS adapter.
- **`OPEN-23` closed:** the sandbox owner is **the project owner (you)**, because no one else is named and I cannot provision one. `docs/M4.3_PLAN.md` §6 and `infra/aws/README.md` carry the runbook (create the role from the committed trust and permission policies, create the document, tag one instance `DcpManaged=true`, register the account and server, run `pytest -m real_integration --integration-profile=nonprod-sandbox`). The `real_integration` marker is added and **excluded from the default run and from CI**. The result is recorded in `PROGRESS.md` as a dated manual check.

### D14 — `OPEN-91` Frontend, and what is deliberately not built
Built: a **Check connectivity** button on the server detail page (visible by the advisory `server:write`, never the control), rendering `reachable` / `not registered with SSM` / `not_configured` / `unsupported` as distinct states with the evidence time; the Actions panel already renders `503` and `422`. `schema.ts` regenerated. **Not built:** a cloud-accounts admin page (the API is complete; an administrator uses it directly until a page is asked for), an inventory-sync button, Azure anything, hybrid `mi-…` hosts (issue 130), `ListCommands` reconciliation (D7), `ExternalId`, the Secrets Manager backend (D2), `max_concurrent_operations` above 1, a retry trigger.

## 5. Security checklist

- No field, task argument, document parameter or setting accepts a command, script, argv, document name, endpoint URL or key; the document name is a constant.
- The document is the only shell line, parameters arrive as environment data, are pattern-constrained at SSM, and are re-validated in the script.
- No static credentials: refused at the factory; no key in settings, database, logs or audit rows.
- A write is sent exactly once; ambiguity is `reconciliation_required`; resume never re-invokes.
- Region, account status, environment snapshot, permission and approval are re-checked by the worker before any provider call.
- Provider text never reaches an exception message, a stored result, a log or a response (a canary sweep covers `sanitized_result`, audit metadata and responses).
- The runtime never attempts a shell document to "prove" a deny.

## 7. Risks

- **A stub proves the code, not AWS.** The error codes, `ListCommandInvocations` fields and the SSM agent's `ENV_VAR` behaviour are from documentation until step 6 above. Mitigation: the status line says so; nothing is called "configured" in §8.
- **SSM Agent version.** `ENV_VAR` interpolation needs a recent agent; on an old one the variables are empty. The script treats empty as invalid and exits non-zero, so it fails closed, but it would fail every operation. The runbook names the minimum agent version to confirm.
- **Latency.** Each read is a Run Command; the pre-flight plus verification add several seconds per operation and consume the account's SendCommand rate. Working defaults, not measurements.
- **Contract edits.** D3 changes a pinned interface and D7 a table. Mitigation: this plan is read before commit 1; the signature test and conformance harness are the proof nothing loosened.
- **Scope.** This is the largest milestone so far. If it must shrink, D12 (the alert) and D14's button are the two cuts that leave the acceptance criteria intact.

## 8. What would change this plan

If you want `AWS-RunShellScript` denial proven at runtime, that requires giving DCP's role `iam:SimulatePrincipalPolicy`, which widens the role the portal holds. If you want accounts discovered and servers auto-registered (D11), environment must then come from somewhere other than a person, which is an authorisation-model decision first. If you prefer Secrets Manager now (D2), say which secret it would hold; today there is none.
