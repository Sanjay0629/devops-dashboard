## 0. What M5.1 is, and what it is not

**Is** (IMPLEMENTATION_PLAN): `deployment_targets` admin endpoints and UI; `GET /deployment-targets`; a Jenkins REST client (trigger with parameters, queue→build resolution, status, console tail) with timeouts, backoff, a circuit breaker, CSRF-crumb handling and the host allowlist; a mock Jenkins in the `mocks` profile. **Acceptance:** only registered targets are selectable; a request naming an unregistered application+environment pair gets `422 not_registered`. **Security:** no Jenkins URL, job name or build parameter is accepted from a request (an adversarial test attempts all three); the token is read from the secret store and never returned; the host allowlist is enforced.

**Is not:** the `deployments` table, `POST /deployments` and the state machine (M5.2 — so **the `422 not_registered` acceptance criterion is met by a resolver function with tests in M5.1, and by an HTTP route only when 21.2 exists in M5.2**; this is stated rather than hidden, see finding 3); polling and the reaper (M5.2); build-log endpoint 19.3 (M5.3); approvals for deployments (M5.4); health-check execution and rollback (M5.5); job-existence verification at registration; a "test this target" button; more than one Jenkins; seeded demo targets.

**The sentence to hold on to afterwards.** After M4.6 a person could read what was done. After M5.1 DCP *knows which pipelines it may run, and can talk to the Jenkins that runs them* — but nothing can be deployed, because there is no deployment to request yet. Like Phase 4's adapters, the Jenkins client is proven against a mock only; no real Jenkins has been called.

## 1. Findings that shaped the decisions

1. **The Jenkins base URL has no home.** `deployment_targets` holds a job path, and `TECH_STACK.md` §6.5 and `SECURITY.md` §19 say "host allowlist on the Jenkins base URL", but no setting, column or document says where that URL lives or whether the allowlist applies the way it does to Prometheus and Loki (it deliberately does not). (D3)
2. **The existing checked-fetch cannot reach a loopback test server.** `address_refusal` refuses loopback outright and `DCP_SSRF_ALLOWED_NETWORKS` "cannot name an always-refused range", so a real HTTP server on `127.0.0.1` cannot be the target of the checked path in a test. Notification delivery got around this with a Compose-network sink; the Jenkins tests need either that or an injected transport. (D14)
3. **The acceptance criterion names a request that cannot exist yet.** "A request naming an unregistered pair gets `422 not_registered`" is §21.2's behaviour, and §21.2 needs the `deployments` table (M5.2). M5.1 ships the resolver and its unit test; M5.2 wires the route. (D1)
4. **The contract has one endpoint for targets and the plan needs five.** `API_CONTRACTS` §21.8 lists targets; there is no create, edit, retire or admin read. (D10)
5. **"Named slots the API may fill" contradicts the §21.2 body.** The body carries `ref` and `reason` only. If a slot meant "any value a request supplies", that would be exactly the arbitrary build parameter PRD §4.10 forbids. (D5)
6. **A Jenkins trigger cannot be made idempotent, and the failure that matters is "I do not know".** A timeout after the POST was sent may or may not have queued a build. M5.2 must reconcile, not retry; the client therefore has to tell *not sent* from *sent, outcome unknown*. (D9)
7. **The cloud error taxonomy says "cloud provider" in its fixed messages** (`providers/errors.py`). Reusing it for Jenkins would put the wrong sentence in front of a user. (D9)
8. **AD-10's schema `CHECK` and an empty health-check config collide in M5.2.** `SUCCEEDED` requires `health_check_result <> '{}'`, and M5.1 can only register `health_check_config = {}`. M5.2 must record an explicit "none configured" result rather than a bare `{}`. Handed over, not solved here. (D8)
9. **A production target with no approval policy would be a path to the PRD §14 non-goal** ("automatic production deployments without approval policies"). The policy `production-deployments` is already seeded by migration `0002`. (D7)
10. **A Jenkins crumb is a read that precedes a write**, and the write must not be retried. Handling the crumb without breaking CLAUDE.md §5's "state-changing provider calls are never blind-retried" needs a stated rule. (D9)

## 2. Decisions (all closed at the recommended option)

### D1 — `OPEN-118` Scope
Built: migration `0014` (`deployment_targets` only); the pure validators and the parameter renderer; endpoints 21.8 – 21.12; the Jenkins client and its settings; the mock Jenkins; the live §26.1 Jenkins row; §18.3's `deployment_targets` section; a Deployment targets page and the application page's section. Not built: see §0. **`resolve_target(application_id, environment)` is a service function that returns the single `ACTIVE` target or raises `422 not_registered`**; it is what §21.2 will call.

### D2 — `OPEN-18` One target per application and environment
Closed as the documents' default: **one non-retired target per `(application_id, environment)`**, a partial unique index on `deleted_at IS NULL`. Retiring a target frees the pair. Canary-versus-full is out of scope and would need a new column and a contract change.

### D3 — `OPEN-119` Where Jenkins lives, the credential, and the allowlist
**One Jenkins per deployment**, configured, not registered: `DCP_JENKINS_URL`, `DCP_JENKINS_USER`, `DCP_JENKINS_TOKEN_REFERENCE` (an `env://NAME` reference; the value arrives as `DCPSECRET_NAME`, resolved per request by `core/secrets.resolve`, never cached, never logged), `DCP_JENKINS_TIMEOUT_SECONDS` (default 10). Unset URL ⇒ `503 not_configured` wherever Jenkins is needed and a `not_configured` §26.1 row.
**Unlike Prometheus and Loki, the URL is checked against the SSRF allowlist** — at start-up (a config validator, the same one that already guards `smtp_host`) and on every call through `pin_to_checked_address` (resolve once, check every address, connect to the checked address, no redirect, no proxy). The reason: Prometheus and Loki are internal monitoring services the operator runs and the product reads; Jenkins is a separate system that holds a credential DCP sends, `SECURITY.md` §19 and `TECH_STACK.md` §6.5 name it, and an unchecked destination plus a token is the case the allowlist exists for. The cost is that local development must list `mock-jenkins` in `DCP_SSRF_HOST_ALLOWLIST` and `DCP_SSRF_INSECURE_HOSTS` and the Compose subnet in `DCP_SSRF_ALLOWED_NETWORKS`, exactly as `notification-sink` already does. Both new settings need a `.env.example` entry **and** a Compose passthrough (issue 54).
The token never appears in a response, an audit row, a log line or an error; the Basic-auth header is built at the call site and the client's `repr` cannot render it.

### D4 — `OPEN-120` The job path
`pipeline_reference` (and `rollback_pipeline_reference`) is `segment(/segment){0,4}` where `segment = [A-Za-z0-9][A-Za-z0-9._-]{0,63}`. A segment cannot start with `.`, so `.` and `..` are inexpressible; there is no `%`, no `?`, no `#`, no whitespace. DCP builds the request path itself as `/job/<seg>/job/<seg>/…`; **the stored string is never concatenated into a URL as written**. The same pattern is a database `CHECK` (defence in depth: a direct `UPDATE` cannot widen it). Never read from a request.

### D5 — `OPEN-121` The parameter template
`parameter_template = {"fixed": {name: string}, "slots": {name: source}}`, `extra="forbid"`.
- `name` matches `[A-Za-z_][A-Za-z0-9_]{0,63}`; at most 20 parameters in total; a name may appear once across both maps.
- `fixed` values are plain strings, ≤ 256 characters, no control characters, and **unchanged by `redact_text`** (the template is returned to administrators and sits in the database, so a secret has no business in it; a value redaction would alter is refused).
- `source` is a **closed enum**: `ref`, `deployment_id`, `environment`, `requested_by` (the user's UUID, not an email). **No slot is filled from a request value except `ref`, and `ref` only after D6.** A `source` the system cannot fill is a `422`.
- If `allowed_ref_patterns` is non-empty there must be **exactly one** `ref` slot (otherwise DCP would validate a ref that never reaches Jenkins and the UI would show "deploying release/1.2" while Jenkins built its default branch); if it is empty there must be none.
`render_parameters(template, *, ref, deployment_id, environment, requested_by) -> dict[str, str]` is pure, and nothing else can enter its result. `deployment_id` is defined now so M5.2 can reconcile a lost build by that parameter; the lookup itself is M5.2's.

### D6 — `OPEN-122` Refs and ref patterns
A ref is a branch, tag or commit and is checked **before any pattern**: `[A-Za-z0-9._/-]{1,200}`, not starting with `-` or `/`, no `..`, no `//`, not ending in `/` or `.`. A 7 – 40 character hex string is a valid ref like any other (and is what lets a commit SHA be requested). A newline cannot appear, which closes the Python `$`-before-trailing-newline edge.
A pattern is ≤ 200 characters, ASCII, at most 10 per target, must compile, and is matched with **`re.fullmatch`** whatever `^`/`$` it carries (so `main` cannot admit `main-evil`, and `^release/` cannot admit `release/../x`, which D6's own grammar already refuses). Refused at registration: look-around, back-references, inline flags, and **any group followed by a quantifier** (the shape of catastrophic nesting). **Ceiling, stated:** this is a restriction, not a proof of linear time; the bound is that the input is capped at 200 characters before any pattern runs. Upgrade path if ever needed: an RE2 binding, which is a new dependency and goes through `TECH_STACK.md` §10 then. `ref_permitted(patterns, ref)` is the one function; empty patterns permit nothing.

### D7 — `OPEN-123` The approval policy link
`approval_policy_id` must name a policy with `applies_to = 'DEPLOYMENT'` **and the same environment as the target** (`422 not_permitted` otherwise). **A `production` target must have one** (`422 approval_policy_required`); a non-production target may have none. M5.1 only validates the link; M5.4 makes it bind. Editing a policy stays §25.13; deleting a referenced one is already refused by the foreign key (checked at commit 4 that §25.14 answers it as a clean `409`, not a `500`).

### D8 — `OPEN-124` Health-check config and rollback fields in this milestone
`health_check_config` is **accepted only as `{}`** (anything else is `422 not_permitted`, "post-deployment checks arrive in M5.5"). Its schema, and its SSRF validation, are defined once, by the milestone that runs it. `rollback_supported` and `rollback_pipeline_reference` are stored and validated (D4), with a **database `CHECK` that they travel together** (`rollback_supported = (rollback_pipeline_reference IS NOT NULL)`, a † addition to `DATABASE.md` §5.1); nothing reads them until M5.5, and DCP never invents a rollback mechanism.

### D9 — `OPEN-125` The Jenkins client
Package `app/deployments/` (the layout `ARCHITECTURE.md` §2 names). **Synchronous** `httpx.Client`: the callers are Celery tasks (M5.2) and the status probe; the one API-path caller (console tail, M5.3) runs it in a thread, as the provider adapters are run. Methods: `probe()`; `trigger(job_path, params) -> QueueRef`; `queue_item(queue_id) -> QueueState` (`waiting | cancelled | started(build_number)`); `build(job_path, number) -> BuildState` (`building`, `result`, `started_at`, `duration_ms`, optional `commit_sha`); `console(job_path, number, offset) -> ConsoleChunk` (raw text ≤ 256 KiB, `next_offset`, `more`). Redaction is the **service layer's** job (M5.3) and `ConsoleChunk` is documented as raw.
- **Trigger:** `POST …/buildWithParameters` expects `201` and a `Location` header; only the **numeric queue id** is parsed from it. The header is never followed and never stored as a URL.
- **Crumb:** fetched from `/crumbIssuer/api/json` immediately before a trigger and sent as the header it names; `404` means "none required". **The trigger is never retried.** A `403` that names the crumb is `crumb_rejected` (the request was refused before acting) and goes to the caller.
- **Not sent versus outcome unknown:** a failure *before the request is written* (DNS, refused address, connect) is `not_sent`; a timeout or reset *after* it is `trigger_outcome_unknown`. M5.2 retries the first and reconciles the second.
- **Reads** are retried at most twice with exponential backoff and jitter (0.5 s, 1 s) on connect errors, read timeouts, `502/503/504` and `429` (a numeric `Retry-After` honoured up to 5 s). Connect timeout 3 s; read timeout `DCP_JENKINS_TIMEOUT_SECONDS`; JSON bodies capped at 1 MiB.
- **Errors:** a new `JenkinsError(reason)` with a closed set (`not_configured`, `provider_unreachable`, `provider_timeout`, `provider_error`, `circuit_open`, `auth_failed`, `job_not_found`, `crumb_rejected`, `trigger_outcome_unknown`), **not** the cloud taxonomy (finding 7). A mapping table gives each its API status (`503 provider_unavailable`, `504 provider_timeout`, `502 provider_error`, `503 not_configured`). A response body is never read into an error, a log line or a response.
- **Circuit breaker:** the existing `CircuitBreaker` class, its own instance. It counts `provider_unreachable`, `provider_timeout` and `provider_error`; a `401`, `403` or `404` is Jenkins *answering*, so it is a success for the breaker and a specific error for the caller. Per-process, with the ceiling the class already states (a Redis-backed breaker is the upgrade).
- No redirects, no environment proxy, `trust_env=False`; the checked-address path of D3 on every call.

### D11 — `OPEN-127` §26.1 and §18.3
§26.1's Jenkins row stops being a placeholder: `not_configured` when `DCP_JENKINS_URL` is unset; otherwise a **live probe** at request time (the Prometheus pattern) with `ok`, or `unavailable` plus the closed reason, and `circuit_state`; `demo_mode` when the mock is the target. §18.3's `deployment_targets` placeholder (`DataSection` `not_configured`) becomes the registered targets for that application, **scoped as 21.8 is**; `[]` and `not_configured` stay distinct states (CLAUDE.md §5). This is a response-shape change to a documented endpoint, so `schema.ts` is regenerated in the same commit.

### D12 — `OPEN-128` The mock Jenkins
`infra/compose/mock-jenkins/mock_jenkins.py`, **standard library only** (a WSGI app, served by `wsgiref` in the container, used directly by tests), on the backend development image like `notification-sink`; `mocks` profile; nothing published to the host. Labelled a development aid, with a README saying passing against it is not evidence a real Jenkins works (CLAUDE.md §7). Behaviour: Basic-auth check; `/crumbIssuer/api/json` (a mode makes it mandatory); a fixed list of known job paths (anything else `404`); `buildWithParameters` → `201` + `Location: …/queue/item/N/`; a queue item that is `waiting` for a configurable number of reads, then `started`; a build that is `building` for a configurable number of reads, then a result; progressive console text with a **planted canary line** for M5.3's redaction test; `/__mock/mode` (`ok`, `outage` → `503`, `slow`, `queue_cancelled`, `build_failure`, `lose_queue_item` → `404` on the queue id after a trigger, `redirect` → `302`) and `/__mock/requests` (every request recorded, for assertions such as "the trigger arrived exactly once"). No seeded demo targets: a fabricated registration would be presented as an operational one.

### D13 — `OPEN-129` Migration `0014`
`deployment_targets` exactly as `DATABASE.md` §5.1, plus: the job-path `CHECK` (D4) on both reference columns; `rollback_supported = (rollback_pipeline_reference IS NOT NULL)` (D8); `jsonb_typeof(parameter_template) = 'object'`; `cardinality(allowed_ref_patterns) <= 10`; `UNIQUE (application_id, environment) WHERE deleted_at IS NULL` (D2); the `status` and `environment` enum `CHECK`s (the project's `enum_check`). No seed rows, no new permission (`deployment:*` and `admin:integrations` exist). The `deployments` table and its foreign key to targets arrive in M5.2's migration. Downgrade and re-upgrade run against real PostgreSQL, hand-reviewed per CLAUDE.md §5.

### D14 — `OPEN-130` How the client is tested
Two layers, because finding 2 forbids a loopback server on the checked path.
1. **Unit and integration, in-process:** the client takes an injectable `transport` and `resolver` (as `ssrf.post_json` does); the mock's WSGI app is mounted with `httpx.WSGITransport`. This runs trigger, queue→build resolution, status polling, console fetch, every mock mode (outage, slow, crumb required, lost queue item, redirect, `401`) and the circuit breaker, in `check-all`.
2. **Compose smoke step:** `scripts/smoke_jenkins.py` runs inside the backend container against the real `mock-jenkins` service over the real network path (resolve, check, pin, connect), including the allowlist refusing a host that is not listed. **It is written in M5.1 and run only if you agree to the smoke script's `down -v` (issue 144); until it is run, the handover says it was not.** The SSRF behaviour on the new call site is also asserted in layer 1 with the existing staged-rebind resolver.
Neither layer is evidence about a real Jenkins. A manual run against a non-production Jenkins with a test pipeline (`TESTING.md` "Real-integration", `IMPLEMENTATION_PLAN.md` Phase 5 prerequisites) is yours to do and is recorded when done, as the AWS check was.

### D15 — `OPEN-131` Frontend
A **Deployment targets** page at `/deployment-targets`: a list for anyone with `deployment:read` (reader shape, with its data states), and for an `admin:integrations` holder a create/edit form — application, environment, pipeline reference, allowed-ref patterns, parameter template (rows for fixed parameters and rows for slots, the slot a closed `<select>`), approval policy (filtered to `DEPLOYMENT` and the chosen environment), rollback pair, status — and a retire action with a confirmation. The application detail page's deployment-targets section shows the real list. **No Deploy button** (M5.2). A banner when Jenkins is `not_configured` or in demonstration mode, so a registered target is never presented as deployable when it is not. Controls are hidden for usability only; the backend decides.

## 5. Security checklist (CLAUDE.md §4)

- [ ] No endpoint, task or client method accepts a URL, a job path, a build parameter or a command from a request (rule 1, rule 9); asserted by an adversarial test and by signature inspection of `JenkinsClient` as M4.1 did for adapters.
- [ ] Every new route has an explicit permission dependency; the route-coverage and audit-completeness gates are green (rule 4).
- [ ] The token is read from the secret store per request and appears nowhere: not in a response, an audit row, a log line, an error, or the bundle (rule 5); canary sweep.
- [ ] Any failure resolving a target, a policy, a scope or the credential denies (rule 6).
- [ ] Every mutation names its initiating identity (rule 7); the audit row carries field names, not values.
- [ ] A Jenkins response, console line or header is untrusted data and never selects what DCP acts on (rule 10); the `Location` header yields a number and is not followed.
- [ ] Every outbound call has a timeout; the trigger is never blind-retried; redirects are not followed; the checked address is the connected address.
- [ ] A production target cannot be registered without an approval policy (D7), so M5.4 has something to enforce.
- [ ] Honest states: not configured, unavailable and "no targets registered" stay distinct in the API and the UI; the mock is labelled and never presented as operational (CLAUDE.md §7).

## 6. Risks

| Risk | Mitigation |
|---|---|
| Jenkins behaves differently from the mock (crumb rules by version, queue item expiry after about five minutes, plugin-specific build parameters) | The mock is a development aid and says so; the real-Jenkins run is the owner's and is recorded; the queue-item-gone case is modelled (`lose_queue_item`) so M5.2's reconcile path has a test fixture |
| The local allowlist wiring (D3) is fiddly and the first run fails for configuration, not code | Same shape as `notification-sink`; the smoke step asserts the *refusal* as well as the success |
| The ref-pattern restriction rejects a pattern an administrator legitimately wants | Refusal names the rule, never the value; the upgrade path (RE2) is written down |
| The application page and dashboard shapes change under the frontend | Types are generated, not hand-edited; `check-all` fails if `schema.ts` drifts |
| Scope creep into M5.2 (a "trigger" route would be tempting for the smoke step) | There is none; the smoke step drives the client directly inside the container |
| A real Jenkins cannot be reached from the development machine | As with AWS: build and prove against the mock, say so, and leave the manual run as a named next step |

## 7. What would change this plan

- You want **more than one Jenkins** (per environment, say): D3 becomes a registered `ci_instances` table and the allowlist check moves to write time per row.
- You want **canary and full targets** side by side: D2 changes, and the unique index and §21.2's body both change.
- You want **job-existence verification at registration**: one read-only `GET …/api/json` in 21.10 / 21.11 and a `422` when the job is absent — small, but it puts an outbound call inside an admin request, so it is left out until asked.
- A **real Jenkins is available for a manual run** before M5.2: do it now; the outcome may change D9's retry and crumb rules.
- You would rather have the request-time `422 not_registered` **as an HTTP route now**: that pulls 21.2 and part of the `deployments` table into M5.1 and ends the milestone's separation from M5.2.

## 8. What differed (written as it happened, commits 2 – 7)

Nothing below changes a decision's intent; each is a thing the plan did not say, found by building or by running.

1. **The table has two more columns than `DATABASE.md` §5.1 listed: `idempotency_key` and `created_by`** (a partial unique index on the pair, the `applications` pattern). §21.10 requires `Idempotency-Key` and a replay returning the original; with no shared key table, the key lives on the row. Recorded in `DATABASE.md` §5.1 as †.
2. **`queue_item` has a fourth state, `gone`.** The plan listed `waiting | cancelled | started`. A `404` on a queue item is not an error: Jenkins forgets an item some minutes after it starts, so "not found" is not "never existed", and the caller (M5.2) reconciles instead of re-triggering.
3. **`destination_refused` joined the closed `JenkinsError` reasons** (ten, not nine): an address the checked path refuses, or a host that has left the allowlist, is neither "unreachable" nor "unavailable" and the integration page should say which.
4. **`may_have_acted` is the field that carries D9's "not sent versus outcome unknown".** A `4xx` and a `429` are refusals (`False`); a timeout, reset or `5xx` after the write, or a `2xx` that cannot be tracked, are `True` and become `trigger_outcome_unknown`.
5. **`If-Unmodified-Since` on §21.11 is optional, exactly as §14.4.** The contract text I wrote in commit 1 said required with `428`; no project route does that. Corrected in `API_CONTRACTS.md`, and the shared helper took a `noun` argument so the message says "deployment target".
6. **A policy with environment `*` is accepted for any environment's target** (D7 said "the same environment"). The seeded policy set uses `*` for operations, and a rule that refused it would have refused a legitimate shape.
7. **§21.8's list uses the project's `page` object** (`limit`, `next_cursor`, `has_more`, `total: null`), not a top-level `next_cursor`: commit 1 had invented a shape; the contract was corrected in commit 4.
8. **§18.5 (archive an application) now refuses while it has a live target.** Not in the plan; found by asking what a registered pipeline for an archived application would be. `409 invalid_state_transition`.
9. **The application page's section is not the §21.8 shape exactly:** it omits `application_id` and `application_name`, which the page already has. `deployment_targets` is `ok` with `items` (`[]` meaning none you may see) or `unavailable` with `deployment_read_not_permitted`; `not_configured` is no longer reported there.
10. **Removing the last endpoint to return the `DataSection` base class removed it from the OpenAPI schema**, so the frontend's `DataSection` alias is now derived from `DeploymentTargetsSection`'s five envelope fields.
11. **`scripts/check_env_example.py` forced a change to the mock's wiring:** the Compose file may not default a variable differently from `.env.example`, so the mock reads `DCP_JENKINS_USER` and `DCPSECRET_JENKINS_TOKEN` with an empty default and applies its own (`dcp`, `mock-jenkins-token`).
12. **The unit-test fixtures moved into `tests/deployments/{harness,conftest}.py`** when the status tests needed them; importing fixtures by name from a test module tripped `F811`.
13. **The landing text still said "Milestone M4.6 … deployments are not implemented".** Updated to say what exists and that Jenkins has been exercised only against a mock.
14. **The project's canary corpus is a test input for templates**: every single-line canary is refused as a fixed value. The three-line PEM canary is skipped, because redaction handles a multi-line key only as a block (issue 92, already pinned).
15. **The first full `check-all` attempt was cut off** (the background launcher was not detached properly); it was run again from a single detached command. Reported so a partial output is not mistaken for a result.
16. **The smoke script was run, but the smoke *test* was not.** `scripts/smoke_jenkins.py` ran green against the real `mock-jenkins` container over the real network path through `docker compose run --no-deps` (no volume was removed). Step 18i is wired into `scripts/smoke-test.sh`, which still needs the owner's agreement to its `down -v` (issue 144) and was not run.
17. **The pages were looked at in the built-in browser** against the running core + mocks stack (`docker compose up --build --wait`, no `down -v`; the development database went to `0014` as `migrate` ran). Seen: the nav link, the list with a staging and a production target, the Jenkins "mock" banner, the Edit form populated from the full detail, the application page's section, and §26.1's Jenkins row `ok` over the real network path. **Not seen:** a form submit by mouse (the pane was not drawing, so clicks went through the DOM); the form's create path is covered by vitest and the API by the integration suite. The synthetic rows were removed again and the services stopped.
