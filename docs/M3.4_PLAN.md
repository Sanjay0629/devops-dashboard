## 0. What M3.4 is, and what it is not

**Is** (IMPLEMENTATION_PLAN): `notification_channels` and `notification_deliveries`, admin endpoints, routing rules, delivery on the `notifications` queue with bounded retry and backoff, delivery status visible in the UI, a manual retry action.
**Acceptance** (PRD §4.8): *notification failures are observable and retryable; destination references come from registered configuration only.*
**Security** (IMPLEMENTATION_PLAN): SSRF controls on webhook destinations (metadata IP, loopback, RFC1918, redirect, DNS rebinding); destination secrets never returned by the API; channel changes audited.
**Is not:** anything in PRD §14; a way to send to a destination a request supplied; Alertmanager receivers (`OPEN-47`: Alertmanager has none, delivery is DCP's own).

## 1. Findings that shaped the decisions

1. **No secret store exists** (`OPEN-06` is still open; `credential_reference` is a column nobody reads). `notification_channels.destination_reference` is, per DATABASE.md §9.2, "a secret-store path for a webhook URL". Something must resolve it.
2. **`core/ssrf.py` is only half of SECURITY.md §19** — its own docstring says the resolved-address check "belongs with the code that performs the fetch". M3.4 is the first code that fetches a registered URL, so the second half lands here.
3. **Alert ingestion is pinned to be inert.** A test asserts `ingest.py`, `store.py`, `webhook.py`, `payload.py`, `lifecycle.py` import nothing that can execute a command, make an outbound call or enqueue a task (SECURITY.md §21). Notification must therefore be *driven from* the alert row without ingestion calling out.
4. **`notification_deliveries` is `UNIQUE (alert_event_id, channel_id)`** — one delivery per (alert, channel). That fixes what can be notified without a schema change.
5. **The API contract has no notification endpoints** (only the audit action `NOTIFICATION_CHANNEL_CHANGED` and a row in §26.1). They are specified here.
6. **`gh` is not installed on this machine**, so the hosted-CI result of PR #21 (M3.3) cannot be read from here. PROGRESS §9 still says "not pushed" although PR #21 merged. I will not claim hosted CI passed; PROGRESS gets corrected to "merged; hosted CI result not verified from this machine" unless you give me the result.

## 2. Decisions (closed, recommended option taken)

### D1 — `OPEN-48` Secret store: a small interface, one real backend (`env://`), one test fake
`app/core/secrets.py`: `resolve(reference) -> SecretStr`, closed scheme set. Built-in backend **`env://NAME`** reads `DCP_SECRET_NAME` from the process environment (injected by the platform); the in-memory fake lives under `tests/`. A reference is validated at write time (scheme, `^[A-Z][A-Z0-9_]{0,63}$`). **The AWS Secrets Manager / Azure Key Vault backends are not built** (they belong with M4.3/M4.4, where the first cloud credential appears); `OPEN-06` stays open and says so. The `env` backend is a development and small-deployment backend, **named as such in PROGRESS §8** — it is not presented as the production secret manager.
*Rejected:* storing the URL in a column (violates OPEN-13 and rule 5); an encrypted column (a second key-management problem).
*Cost:* the worker and the API both need the variable (the API resolves at write time to validate, the worker at send time).

### D2 — `OPEN-49` Outbound fetch: finish SECURITY.md §19
New in `core/ssrf.py` (no new dependency): `resolve_and_check(host)` and `post_json(...)`. Resolve the name, check **every** returned address, connect to the **checked address** (URL rewritten to the literal IP, original `Host` header, `sni_hostname` extension so TLS still verifies the name — this is the DNS-rebinding defence: there is no second lookup to walk). `follow_redirects=False`; a 3xx is a permanent failure. Timeout 10 s total, 3 s connect, response read capped at 64 KiB and **never stored or echoed**.
**Always refused:** loopback, link-local (including `169.254.169.254` and its IPv4-mapped form), unspecified, multicast, reserved, IPv4-mapped/6to4 equivalents. **Refused unless allowlisted:** RFC1918, CGNAT, IPv6 ULA — via a new `DCP_SSRF_ALLOWED_NETWORKS` (CIDR list, default empty = none; `0.0.0.0/0` and any range overlapping an always-refused one refused at startup, like `alert_webhook_allowed_cidrs`). The host allowlist and `https`-only rule already in `validate_registered_url` stay (exact match, no suffix).
*Ponytail note:* the helper is generic on purpose — the health-check runner (M5) and Jenkins (M5) need the same one; it is not a notification-only abstraction.

### D3 — `OPEN-50` How an alert drives a notification: a transactional outbox, not an enqueue
`store.fire()` already returns `"created"` inside the alert's transaction. In that same transaction a pure-SQL function (`app/notifications/routing.py`) inserts one `PENDING` `notification_deliveries` row per matching `ACTIVE` channel (`ON CONFLICT (alert_event_id, channel_id) DO NOTHING`). **It enqueues nothing and calls nothing**, so the M3.3 import-pin test keeps holding (and is extended to cover `routing.py`). A beat task, `dcp.notifications.dispatch`, every **15 s** on the `notifications` queue, claims due rows and enqueues `dcp.notifications.deliver(delivery_id)` — **ids only** (SECURITY.md §22). A lost enqueue heals itself (see D6: the claim is a lease). This also is ARCHITECTURE.md §2.3's "notification retry drain" — one mechanism for first send and retry.
*Cost:* up to ~15 s added latency, accepted (alerts here are minutes-scale: `for:` 1 – 10 min).
*Rejected:* enqueueing from the webhook (breaks the pinned inertness and couples a `202` to the broker); a DB trigger (hidden, untestable in the app layer).
**Consequence, stated:** SECURITY.md §21's sentence "triggers no outbound call" stays true *of ingestion*; a crafted alert can now cause a message to **registered channels only**, with DCP-rendered, escaped, length-capped content (D8). The M3.3 adversarial test is extended to assert exactly that and nothing wider.

### D4 — `OPEN-51` What is notified: a new alert row only
A notification is created when an alert **row is created** (`created`), including an escalation (a resolved warning and a new critical are different rows, `OPEN-41`). **Not notified in v1:** repeats (`occurrence_count`++ — that is the deduplication PRD §4.8 asks for), `ACKNOWLEDGED`, `RESOLVED`, `EXPIRED`. This keeps the documented `UNIQUE (alert_event_id, channel_id)` untouched. "Resolved" notices are a real operational want; adding them is one migration (a `kind` column in the uniqueness) and is listed under *Not M3.4*, not silently half-built.
*Stated honestly in the UI and docs:* a channel hears that a problem began, not that it ended.

### D5 — `OPEN-52` Routing rules
`routing_rules` JSON, validated by Pydantic `extra="forbid"`: `severity` (subset of `INFO|WARNING|CRITICAL`), `environment` (subset of the four environments), `target_type` (subset of `server|service`). **An absent or empty dimension means "no restriction on that dimension"; `{}` is a catch-all** (matches the column default). A channel that restricts `environment` **does not receive an alert with no resolved environment** (unlinked and `DCP_SYSTEM` alerts) — the same fail-closed stance as `OPEN-45`, so a payload cannot place itself into an environment's channel by claiming one. Matching is a pure function of (channel rules, alert severity/environment/target_type), all three taken from the stored row, never the payload.
*Stated:* a channel delivers alert content to an external destination regardless of any reader's scope; only an Administrator (`admin:integrations`) can register one.

### D6 — `OPEN-53` Delivery states, retry, abandonment
Mapping of the four schema statuses (and an amendment to TESTING.md §7's ambiguous sentence):

| Status | Meaning | Automatic retry | Manual retry |
|---|---|---|---|
| `PENDING` | not yet sent, or waiting for a retry (`next_attempt_at`) | yes | — |
| `SENT` | destination accepted it (`2xx` / SMTP accepted) | — | **no** (409; never a duplicate by button) |
| `FAILED` | **permanent** failure | no | yes |
| `ABANDONED` | **transient** failures exhausted the cap | no | yes |

**Claim = lease**: a short transaction sets `attempt_count += 1` and `next_attempt_at = now + 120 s`, then the send happens with no transaction open (DATABASE.md §12), then a second short transaction records the result. A worker that dies mid-send leaves a row that becomes due again — **at-least-once, so a duplicate message is possible and is documented** (the alternative, at-most-once, silently loses an alert). `FOR UPDATE SKIP LOCKED`, batch of 50 per tick, ordered `CRITICAL` first.
**Schedule:** 5 attempts at +0, +1 min, +5 min, +15 min, +60 min after each failure; the fifth failure → `ABANDONED`. A `429` honours `Retry-After`, capped at 1 h, never shorter than the schedule.
**Transient:** timeout, connect failure, `5xx`, `429`, `408`, SMTP `4xx`. **Permanent:** other `4xx`, any `3xx`, an SSRF refusal, an unresolvable secret reference, an invalid address, SMTP `5xx`, channel `DISABLED` at send time (re-checked by the worker — rule 3's pattern).
**`last_error` is a closed reason code** (`http_404`, `timeout`, `connect_failed`, `destination_refused`, `secret_unresolvable`, `smtp_rejected`, `redirect_refused`, …) — **never the URL and never the peer's own words** (the Alertmanager-row precedent), so it can be shown to an `alert:read` holder without leaking infrastructure or a token.
**Manual retry** resets `attempt_count` to 0 and sets `PENDING` due now; the audit row records the previous count and status. Only `FAILED`/`ABANDONED` are retryable; a row in flight is `409`.
**Retention:** a `dcp.maintenance.purge_notification_deliveries` task deletes rows older than 90 days (DATABASE.md §11; a plain `DELETE`, unlike the partition drops that remain unbuilt, issue 107).

### D7 — `OPEN-54` Email transport
`smtplib` (stdlib) from the worker, `email.message.EmailMessage` (refuses header newlines), settings `DCP_SMTP_HOST/PORT/FROM/USERNAME`, `DCP_SMTP_PASSWORD` (`SecretStr`), `DCP_SMTP_STARTTLS` (default **true**; refusing to send in clear except to a host also in `ssrf_insecure_hosts`). The recipient is the channel's `destination_reference` — a single, strictly parsed address (no display name, no list, no CR/LF, ≤ 254 chars). **The SMTP host is deployment configuration, not a request value**, so it gets the host-allowlist and resolved-address check of D2 at connect time too (connect to the checked IP). Unset `DCP_SMTP_HOST` ⇒ an `EMAIL` channel cannot be created (`422 not_configured`) and the integrations row says so.

### D8 — `OPEN-55` Message content is untrusted text
Alert `summary`, labels and annotations come from outside. The renderer builds a fixed template from **stored, already-redacted** fields (rule name, severity, status, environment, summary ≤ 300 chars, server/service id, optional link). Escaping per channel: Slack `& < >` (blocks `<!channel>` and `<url|text>`), Teams/webhook as JSON strings, email as `text/plain` only (no HTML part). `link` is `DCP_PUBLIC_BASE_URL + /alerts/{id}` and **omitted when unset** (no base URL exists today; it is not derived from the OIDC redirect URL). Payload formats for Slack/Teams are written from their public documentation and are **not verified against a real workspace** — recorded as such.

### D9 — `OPEN-56` Permissions, audit, endpoints (contract additions)
No new permission. **Channel admin: `admin:integrations`** (Administrator-only, like cloud accounts, `OPEN-27`). **Delivery visibility on an alert: `alert:read`**, inside that alert's scope (otherwise the same `404`). **Manual retry: `alert:acknowledge`**, inside scope — the on-call operator, not only an administrator. Retry is a state-changing route, so it is blocked in read-only mode like its neighbours.
Audit: `NOTIFICATION_CHANNEL_CHANGED` (create, edit, enable/disable; metadata = changed field *names* and channel type, **never the reference value**), and a new `NOTIFICATION_RETRY_REQUESTED` (the catalogue is extensible). Automatic sends are not privileged operations — they change nothing in the estate; the record is `notification_deliveries`, acting identity `system:notifications` in logs.

| # | Method | Path | Permission |
|---|---|---|---|
| 26.8 | GET | `/api/v1/notification-channels` | `admin:integrations` |
| 26.9 | POST | `/api/v1/notification-channels` | `admin:integrations` |
| 26.10 | PATCH | `/api/v1/notification-channels/{id}` | `admin:integrations` |
| 20.6 | POST | `/api/v1/alerts/{alert_id}/notifications/{delivery_id}/retry` | `alert:acknowledge` |

Plus: §20.2 gains `notifications[]` (channel name and type, status, attempt count, closed `last_error`, `next_attempt_at`, `sent_at`); §20.1's existing `coverage` gains `notification_channels_active` (an honest "alerts are not sent anywhere" banner when `0`); §26.1 gains **one row per channel**. Channel responses return the reference **as registered** (for `env://` it is a name, not a value) plus type/status/routing/recent-delivery counts, and never a resolved value. Body models `extra="forbid"`; a request containing a URL-shaped or secret-shaped value in `destination_reference` is `422 credentials_must_be_stored_in_secret_manager`, not echoed.
**Integrations row semantics** (the page that answers "is the portal broken or the thing it monitors?"): newest finished delivery `SENT` ⇒ `ok`; newest `FAILED`/`ABANDONED` ⇒ `unavailable` (reason code); no delivery ever attempted ⇒ **`degraded` with `no_delivery_attempted_yet`** (unproven is not `ok`; this is the first use of `degraded`, which M2.1 held back because nothing could decide it — a persisted delivery history can); `DISABLED` ⇒ `not_configured` (`channel_disabled`); no channels at all ⇒ one `Notification channels` row, `not_configured`.

### D10 — `OPEN-57` Deliberately not built
No delete (RESTRICT FK; disable instead). **No "send test message" and no "verify" endpoint** — a test delivery needs an alert row (the FK is `NOT NULL`), and a synthetic one is the mocked-data pattern CLAUDE.md §7 forbids; a configuration error shows as a `FAILED` delivery with a reason code. No per-channel rate limit or digest (a fleet outage sends one message per alert; Slack's `429` is handled by backoff). No webhook HMAC signing, no secret rotation, no escalation/quiet hours, no per-user email (assignee).

## 4. Tests (written with the code, failure and authorisation paths included)

*Unit:* routing matrix (every dimension, empty, unlinked alert vs environment-restricted channel); backoff table and the cap; failure classification table; renderers (Slack `<!channel>`, `<url|x>`, markup, 10 000-char summary, control characters); address parser (CRLF, list, display name, over-length); secret-reference grammar; address-class table for the SSRF check (loopback, `169.254.169.254` and its IPv4-mapped spelling, RFC1918 allowed/not, ULA, multicast, `::ffff:` forms); startup validation of the new settings.
*Integration (real PostgreSQL/Redis):* exactly one delivery per (alert, channel) under concurrent ingestion; a repeat adds none; a resolved alert adds none; success; transient-then-success; permanent → `FAILED`; five transients → `ABANDONED`; manual retry (legal and illegal states, scope, race of two retries = one winner); **worker re-check** (channel disabled, or reference removed, between claim and send ⇒ refused, nothing sent); redirect refused; **rebinding** with an injected resolver (public on the first lookup, private on the second ⇒ still connects only to the checked address); lease expiry resends; two workers, one row ⇒ one send; scope matrix on `notifications[]`; route-coverage and the permission matrix for the four routes; read-only mode.
*Security (the gate):* a canary secret URL in `DCP_SECRET_*` is absent from every API response, audit row, `last_error`, log line and Celery task payload; a crafted alert changes no server, service, grant, audit action type and reaches no destination except registered channels; tasks accept ids only; no `pickle`; the sink never receives from a host outside the allowlist.
*Frontend:* every state of both pages, markup in a summary and in a channel name, every error, the retry button's enabled/disabled states, permission gating, the reference field never showing a value.
*Smoke 18h* as in commit 4. **Mutation checks, each seen failing:** SSRF address check removed; redirect following on; lease removed (double send); `ON CONFLICT` replaced by check-then-insert; reason code replaced by the raw error text; empty routing treated as "match nothing".

## 6. Risks

1. **Compose network vs. `DCP_SSRF_ALLOWED_NETWORKS`:** the sink is on a private address; the dev default allows the Docker bridge ranges (as the webhook CIDR default does) and says so. If the CI runner's subnet differs, smoke 18h fails closed rather than widening the check.
2. **Smoke test length:** 18h adds a sink stop/start and one retry wait; the retry schedule is overridable for the smoke run only through a setting that asserts the worker sees it (the M2.3 interval precedent), never by a code path.
3. **At-least-once** duplicates (D6) — documented, not hidden.
4. **`env://` secrets are not a secret manager** (D1) — said in PROGRESS §8.
5. **Contract additions** (26.8 – 26.10, 20.6, `notifications[]`, `coverage` field, the first `degraded`) are new client-visible surface; additive only (AD-17).
