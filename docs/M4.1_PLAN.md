## 0. What M4.1 is, and what it is not

**Is** (IMPLEMENTATION_PLAN): the `ProviderAdapter` interface, result envelope and error taxonomy; capability sets; an adapter registry keyed by `cloud_accounts.provider`; `DemoAdapter`; `GET /cloud-accounts/{id}/capabilities` (§26.7); `demo_mode` propagation.
**Acceptance:** no provider-specific branching above the adapter layer (reviewed **and** grep-checked); demonstration mode returns `not_configured` for writes and marks every affected response.
**Security:** the interface exposes **no** command, script, argv or document parameter — enforced by the signature itself.
**Is not:** a real provider (AWS M4.3, Azure M4.4), the operation state machine (M4.2), approvals (M4.5), §14.8, §26.2 – §26.6, or any frontend page. No migration, no new dependency, no new setting, no new audit action: M4.1 changes no table and writes nothing.
**Prerequisites check** (IMPLEMENTATION_PLAN Phase 4): the cloud account with a scoped role and the reviewed SSM document gate M4.3, and `OPEN-10` gates M4.5; neither gates M4.1. `OPEN-05` does gate M4.1 and is closed in D5.

## 1. Findings that shaped the decisions

1. **The documents contradict each other on the demo adapter.** `ARCHITECTURE.md` §7.2 says Demo connectivity is "Always ok" and service control is "Simulated"; §7.3 and `TESTING.md` §6 say Demo returns `NotConfigured` for writes; `API_CONTRACTS.md` §14.8 says `503 not_configured` in demonstration mode. `CLAUDE.md` §7 ("never present a mocked integration as operational") breaks the tie. Closed in D6.
2. **"A full operation lifecycle against `DemoAdapter`" (IMPLEMENTATION_PLAN) cannot be run in M4.1.** Writes are `not_configured` by the same milestone's acceptance criterion, and the state machine is M4.2. Re-scoped in D6.
3. **The `ProviderAdapter` class diagram has `execute_operation(ref, action, params)`.** A `params` bag is the exact shape a shell path hides in. The signature has to change in the contract, in the same change as the code (D1).
4. **Provider names already exist above the adapter layer**, so the grep gate cannot be "no occurrences". `inventory/schemas.py` holds a per-provider resource-id regex and a provider → allowed-`management_method` table; `inventory/models.py`, `seed.py`, `dashboard/router.py` and `router_servers.py` hold the closed enum. Closed in D8, and the point most worth your attention.
5. **`ARCHITECTURE.md` §10.2 is ambiguous for writes.** `ProviderUnavailable` is "Yes, retry", while `CLAUDE.md` §5 says state-changing provider calls are never blind-retried. Closed in D3.
6. **Workers are synchronous** (`get_sync_engine`, plain Celery tasks); the API is async. `boto3` is synchronous. Closed in D1.
7. **There is no cloud-account router.** §26.2 – §26.6 do not exist, so nothing in the UI or API can discover an account id; 26.7 is reachable only by id. Stated in D7, not worked around.
8. **§26.1's single "Cloud accounts" row says "No cloud provider adapter exists yet (M4.1)".** That sentence becomes false the moment M4.1 lands.

## 2. Decisions (closed, recommended option taken)

### D1 — `OPEN-58` The interface: synchronous, typed, and gated by a method adapters cannot skip
New package `backend/app/providers/`. `ProviderAdapter` is an ABC.
- **Synchronous.** Workers are sync and `boto3` is sync; the API calls the two short read methods through `anyio.to_thread` (the 10 s budget, ARCHITECTURE §10.1). *Rejected:* an async interface (it would force `asyncio.run` into every Celery task).
- **Typed signature, no free-form parameter.** `get_server_info(ref: ServerRef)`, `check_connectivity(ref)`, `list_managed_services(ref)`, `execute_operation(ref: ServerRef, service: ServiceRef, action: ServiceAction, *, operation_id: UUID) -> ExecutionHandle`, `get_operation_status(handle: ExecutionHandle)`. `ServerRef` and `ServiceRef` are frozen value objects built **from stored rows only**; `ServiceRef.unit_name` is validated in its constructor against the same pattern as the `services.service_name` CHECK (defence in depth, not the control). `ServiceAction` is the closed enum `start | stop | restart | status | logs_tail`. The ARCHITECTURE §7 diagram drops `params`.
- **`execute_operation` is concrete and final on the base class**: it checks the capability for `action` (D4) and only then calls the abstract `_submit(...)`. A new adapter therefore cannot forget the gate, and capability gating is tested once. `__init_subclass__` refuses a subclass that overrides `execute_operation`.
- **Signature test (the SECURITY requirement):** inspect every public method of the ABC and every registered adapter; every parameter annotation must be a member of a closed set (`ServerRef`, `ServiceRef`, `ServiceAction`, `ExecutionHandle`, `UUID`); no `str`, `dict`, `Any`, `*args` or `**kwargs`; no parameter named like `command`, `script`, `argv`, `args`, `shell`, `document`, `params`. Stronger than a name check, because a new parameter must be added to the allowed set on purpose.
- **No timeouts in the interface yet.** `DemoAdapter` makes no outbound call; every real adapter's timeouts land with it (M4.3), constants taken from ARCHITECTURE §10.1.

### D2 — `OPEN-59` The result envelope
`AdapterResult[T]`: `value`, `data_state` (`ok | stale | unavailable | unsupported | not_configured`, the §4 vocabulary), `collected_at`, `adapter_id`, `demo_mode`, `reason` (closed code or `None`). **`demo_mode` is set by the adapter that produced the result** (`DemoAdapter` sets it `True`, always, in a place a subclass cannot forget), not read from settings at the API edge — so a result keeps its flag through a queue or a log. `value` is `None` whenever `data_state` is not `ok` or `stale` (the honest-null rule: unknown is never a substitute value). `ExecutionHandle` is `{adapter_id, external_execution_id, submitted_at}`; `external_execution_id` is bounded (`^[A-Za-z0-9._:/-]{1,256}$`) and is what M4.2 persists **before** polling (AD-08).

### D3 — `OPEN-60` Error taxonomy, API mapping, and a retry table that separates reads from writes
Nine exceptions under `ProviderError`, exactly ARCHITECTURE §7.1, each carrying a fixed operator-safe message and a lowercase `provider_error_class` (API_CONTRACTS §3). **The provider's own text is never copied into a message or `details`** (SECURITY §20); an optional `detail_code` is a closed code. Mapping, in `providers/errors.py`, to `AppError`:

| Error | HTTP · code | Notes |
|---|---|---|
| `AuthenticationError` | 502 `provider_error` | a configuration problem, class `authentication` |
| `AuthorizationError` | 502 `provider_error` | class `authorization` |
| `NotFound` | 502 `provider_error` | **not** 404: a 404 says DCP's own resource is absent; this says the provider no longer has it (stale inventory) |
| `Throttled(retry_after)` | 503 `provider_unavailable` + `Retry-After` | not 429, which is the caller's own rate limit |
| `Timeout` | 504 `provider_timeout` | |
| `UnsupportedOperation` | **422 `unsupported_operation`** (new row in §3) | PRD §4.11: never a generic failure; the one code with no provider-error envelope |
| `PartialFailure` | 502 `provider_error` | per-target detail retained as closed codes |
| `ProviderUnavailable` | 503 `provider_unavailable` | |
| `NotConfigured` | 503 `not_configured` | reuses the existing `NotConfiguredError` code |

**Retry table** (data, pinned by a test; no executor until M4.3): read retry — `Throttled`, `Timeout` (2), `ProviderUnavailable`; `AuthenticationError` once after a forced credential refresh. **Write retry — `Throttled` and the single authentication refresh only**, because both mean the provider refused the request *before* acting. `Timeout` and `ProviderUnavailable` on a write are **reconcile from the persisted handle, never retry** (CLAUDE.md §5; the ambiguity in finding 5). §10.2 is amended into read and write columns in commit 1.

### D4 — `OPEN-61` Capability sets: three-valued, not boolean
`CapabilitySet`: `inventory_sync`, `connectivity_check`, and one entry per `ServiceAction`, each a `Support` of `supported | unsupported | not_configured`; plus `async_handle: bool`, `concurrency` (`none | per_target_serialised | account_throttled | adapter_defined`) and `latency` (`immediate | seconds | tens_of_seconds`). Why three: `unsupported` means the provider cannot do it ("not supported by this provider", PRD §4.11); `not_configured` means we have not set it up. Merging them is the exact confusion the §4 `data_state` vocabulary exists to prevent. `ensure_supported(caps, action)` raises `UnsupportedOperation` or `NotConfigured` accordingly and is what the base class calls.
**Demo:** `inventory_sync`, `connectivity_check` and all five actions are `not_configured`; `async_handle=False`; `concurrency=none`; `latency=immediate`. The matrix is pinned against the §7.2 table by a test. **Stated limit:** with one adapter there is one column; the "adapters differ where they genuinely differ" assertion (TESTING §6) can only be written when a second real adapter exists, so M4.1 builds the parametrised harness and M4.4 adds the disagreement assertions. M4.1 does not claim that test.

### D5 — `OPEN-62` Registry, and `OPEN-05` (the restricted agent)
`providers/registry.py`: `resolve_adapter(provider: str) -> ProviderAdapter`. In `demo_mode` it returns `DemoAdapter` for every provider. Otherwise it consults a mapping of provider → factory that is **empty in M4.1** (M4.3 adds `AWS`, M4.4 `AZURE`), and **an unregistered or unknown provider raises `NotConfigured` (fail closed, CLAUDE.md rule 6)**. The registry is keyed on `cloud_accounts.provider` as IMPLEMENTATION_PLAN says; a server's `management_method` is the adapter's concern, not a second registry key. `demo_mode` cannot be true outside `local` (already enforced in `config.py`), so demo and real adapters never mix in a deployment.
**`OPEN-05` closed:** the working default stands — **adopt, do not build**. No `AgentAdapter` in M4. `ON_PREM` / `OTHER` accounts resolve to no adapter (`not_configured`), which matches what registration already allows them (`RESTRICTED_AGENT | NONE` only). *Recorded as a gap, not solved:* SSM hybrid activations would put an on-premises host under an AWS adapter with an `mi-…` resource id, which the current `^i-` pattern in `inventory/schemas.py` rejects; that is an M4.3 / M6.1 question and is noted under *Not M4.1*.

### D6 — `OPEN-63` What the demo adapter may say (resolves finding 1 and 2)
**Rule: the demo adapter never asserts a fact about a host.** It answers what is true of itself and raises `NotConfigured` for anything that would state the condition of a real thing.
- `capabilities()` — answers (D4), flagged `demo_mode`.
- `get_server_info(ref)` — returns the identity the caller already holds (resource id, region) plus `provider_status="demonstration"`; it invents nothing.
- `check_connectivity`, `list_managed_services`, `execute_operation`, `get_operation_status` — **`NotConfigured`**. An "always ok" connectivity result would present a mock as operational (CLAUDE.md §7), and an empty service list is the "no logs found" lie in a new place. `ARCHITECTURE.md` §7.2's Demo column ("Always ok", "Simulated", "Synthetic") is amended to match, and the amendment says why.
- **Synthetic data stays where it already is**: the `[DEMO]`-labelled rows from `inventory/seed.py`. The adapter does not grow a second fake fleet.
- **§14.8 is not built in M4.1.** It needs a rate limit, an audit action, a server-scope check and a real adapter to be worth calling; with Demo it can only return `503 not_configured`. It moves to M4.3. (IMPLEMENTATION_PLAN M4.1 does not list it; the M1.5 note only said it needed "the first adapter".)
- **"A full operation lifecycle against `DemoAdapter`" is re-scoped:** M4.1's integration test drives the adapter lifecycle (capabilities → server info → connectivity → services → execute → status) and asserts each outcome above, and that **no handle exists** after a refused execute. The state-machine lifecycle (request → `SUCCEEDED` with `observed_state_after`) belongs to M4.2 and runs there against a **test-only** `ScriptedAdapter` in `tests/providers/` — never in `app/`, so it cannot be mistaken for an integration.

### D7 — `OPEN-64` §26.7, and the §26.1 row
`GET /api/v1/cloud-accounts/{id}/capabilities`: `admin:integrations` (a no-target permission, like channel administration), read budget, no audit row (a read), unknown query parameters rejected. A soft-deleted or unknown id is `404`. Shape: `{account_id, provider, account_status, adapter_state (demonstration | not_configured), adapter_id | null, capabilities | null, data_state, reason, demo_mode}`.
- Demo mode → `adapter_state=demonstration`, `data_state=ok` (the capability set is a true statement about the demo adapter), every action `not_configured`, `demo_mode=true`.
- No adapter for the provider → **`200`**, `adapter_state=not_configured`, `data_state=not_configured`, `capabilities=null` (null is unknown, never an empty set that reads as "supports nothing"), `reason=no_adapter_for_provider`. A `503` would hide the one fact an operator needs.
- `account_status` is reported, not enforced here; the DISABLED gate is SECURITY §14 step 3 in M4.2.
- Lives in `providers/router.py` (tag `cloud-accounts`); M4.3 adds §26.2 – §26.6 beside it.
- **§26.1 stays a single row** (finding 8). Only its reason text changes: it reports demonstration mode or "no adapter is implemented for the provider yet (M4.3 / M4.4)". Per-account rows arrive with §26.5 (a real probe), as the existing note in API_CONTRACTS already says. *Rejected:* per-account rows now, which would be N copies of one "no adapter" fact.
- No frontend page. `npm run generate:api` regenerates `schema.ts`; the consumer is the M4.2 confirmation dialog.

### D8 — `OPEN-65` The "no provider branching above the adapter layer" gate (the decision most worth your attention)
`scripts/check_provider_branching.py`, wired into `check-all.sh` as `providers: no branching above the adapter layer`: scan every `backend/app/**/*.py` outside `app/providers/` for `boto3`, `botocore`, `azure`, `ssm`, `AWS`, `AZURE`, `AWS_SSM`, `AZURE_RUN_COMMAND`, `AZURE_ARC`, `ON_PREM` (word-bounded, case-sensitive where case matters). A file may contain them only if it is in an **explicit allowlist with a reason per entry**; a hit anywhere else fails the check, and a test asserts the allowlist is exactly the reviewed set so it cannot grow silently. Expected allowlist, from today's code: `inventory/models.py` (the closed enums), `inventory/schemas.py` (registration validation — below), `inventory/seed.py` (labelled demo data), `dashboard/router.py` and `inventory/router_servers.py` (filter literals), `core/redaction.py` (an AWS key-id pattern), `core/secrets.py` (a docstring).
**Review finding, stated plainly:** `inventory/schemas.py` does contain provider-specific logic above the adapter — `_RESOURCE_ID_PATTERNS` (what an instance id looks like per provider) and the provider → `management_method` table. I judge it **registration-time validation of closed data, not behavioural branching** (no `if provider == …` chooses a code path that touches a provider), and I recommend leaving it: moving it into the adapters touches M1.5's validation and its tests, which is the "unrelated refactoring" CLAUDE.md §3 rules out. The honest reading of the acceptance criterion is therefore "no *behavioural* branching", and the allowlist makes the exception visible instead of invisible. It goes into `PROGRESS.md` §6 as a known issue with the trigger to revisit it (M4.3, when an adapter exists that could own `ServerRef` validation). *Alternative:* move both tables behind the adapters now — more faithful to the letter, a wider diff, and it needs an adapter that does not exist yet to own the AWS patterns.

### D9 — `OPEN-66` Deliberately not built
`AgentAdapter` (D5); §14.8 (D6); §26.2 – §26.6 and any account UI; per-account §26.1 rows; any real provider, credential, secret backend or outbound call; timeouts, circuit breakers and retry execution (they arrive with the first adapter that has something to time out); the capability-disagreement assertions (M4.4); a `ScriptedAdapter` in `app/`; hybrid-activation (`mi-…`) support.

## 5. Security checklist for this milestone

- No parameter on any adapter method can carry a command, script, argv or document name — asserted by signature inspection, not by review.
- `execute_operation` cannot skip the capability gate (final method + subclass guard).
- Unknown provider ⇒ `NotConfigured` (fail closed); an adapter result never substitutes a value for an unknown.
- No provider text in any error message or `details`; no credential, reference or account identifier beyond the already-stored `account_reference` appears in the 26.7 response.
- `admin:integrations` enforced on the route, covered by the route-coverage meta-test.
- `demo_mode` is carried by the result, and the 26.7 response says so.

## 6. Risks

- **A vacuous harness.** A conformance suite that nothing ever fails proves nothing; commit 3 includes an adapter written to violate it.
- **A vacuous gate.** The provider-branching check passing because the scan found no files; the test asserts a planted violation is caught and that the allowlist files are all actually scanned.
- **Contract drift.** Four documents change in commit 1; `check_doc_links.py` and a review of each diff against its neighbours is the control.
- **Over-claiming.** Zero real provider code exists after M4.1. The only honest summary is "the seam exists and is tested against a demonstration adapter and a test fake".

## 7. What would change this plan

If you prefer D8's alternative (move the provider tables behind the adapters now), commit 4 grows by the `inventory/schemas.py` change and its tests and the allowlist loses two entries. If you want §14.8 in this milestone, it adds a route, a rate limit, a new audit action (`SERVER_CONNECTIVITY_CHECKED`) and a scope-checked server lookup, and it would still answer only `503 not_configured`.
